## 全体構成：オフライン事前生成 ＋ 実行時テーブル参照

チューリング・アントは決定論的だが初期配置のわずかな違いで結果が非連続に飛ぶ(カオス的)ため、CPUの意思決定を**実行時にオンライン探索**すると計算コストが読めず、リアルタイム性を阻害する。探索そのものは**開発時にオフラインで前借り**し、実行時は生成済みテーブルと学習済み方策を参照するだけにする。

**プレイヤーも同じテンプレート集から選ぶ。** 良い配置は乱数探索で見つかる確率が低く、人間が手で見つけるのは事実上不可能な一方、CPUはオフライン探索の答えを持っている。同じ土俵に立たせないと勝負が成立しない。

### `src/search/` のモジュール構成(v4)

MAP-Elites 探索用の型・変異・アーカイブ。いずれも DOM は勿論、`src/engine.js` も import しない純粋なデータ操作(テンプレート生成というオフライン専用の関心事を `src/engine.js` から切り離すため)。

| モジュール | 役割 |
|---|---|
| `src/search/genome.js` | 探索対象の genome 表現(`rule`/`antX`/`antY`/`antDir`/`cells`)。生成・検証・複製・キー化・`templates.json` 用変換 |
| `src/search/mutate.js` | genome への突然変異オペレータ(rule の伸縮・ビット反転、セルの追加/削除/移動/状態変更、アリの初期位置/向き変更) |
| `src/search/map-elites.js` | アーカイブの汎用実装(`createArchive`/`tryInsert`/`sampleParent`/`runMapElites`)。評価関数(`evaluate`)は呼び出し側が渡す |

依存関係: `map-elites.js` が `genome.js`(`createRandomGenome`)と `mutate.js`(`mutate`)を import する。`mutate.js` は `genome.js`(`cloneGenome`)に依存する。いずれも `src/config.js` から数値定数を引く。

> ⚠️ 作業指示にある「`src/search/` の6モジュール(`genome`/`mutate`/`highway-detector`/`map-elites`/`evaluate-projectile`/`evaluate-interaction`)」のうち、実在するのは上の3つのみ(本稿執筆時点)。
> - ハイウェイ検出は独立ファイルではなく `src/engine.js` の `detectHighway()` にある([data-model.md](data-model.md) 参照)。
> - `evaluate-projectile.js`(`evaluateProjectile`)と `evaluate-interaction.js`(`evaluateInteraction` / `buildCounterMatrix` / `buildEscortTable`)は**実装済み**。前者は genome 1件を「探索評価(20,000ステップ)＋ゲーム評価(寿命2,400)」にかけて記述子と quality を返し、後者は 攻撃 × 妨害 × 発射タイミング の相互作用から `counterTable` / `escortTable` を組み立てる。
> - ⚠️ ただし `scripts/generate-templates.mjs` はまだこれらを import しておらず、旧来のローカル関数(`soloScore`/`isCountered`/`countCounters`)を使ったままになっている。この配線が次の作業対象(後述)。
>
> `data/search-archive.json` に書き出す呼び出し元も未実装。

## 主要な設計判断

| 判断 | 選択 | 理由 | 代替 |
|---|---|---|---|
| アリのルール | **v4: アリ(テンプレート)ごとに `rule`(`'L'/'R'` 文字列、色数2〜16)を持つ。グローバル固定の `RULE` は廃止** | 固定1ルールだと探索空間が狭く、MAP-Elites で多様なハイウェイ(方向・速度・形成時間)を見つける余地が無い | v3.1: 全アリ共通で **RRL(3色)固定**。38ステップでハイウェイを形成した(実測。`src/config.js` の `LEGACY_RULE`/`LEGACY_HIGHWAY_ONSET_STEP` として回帰フィクスチャに残存。⚠️「全アリが38ステップでハイウェイになる」という意味ではなく、`LEGACY_RULE` を選んだアリの軌道が従来と同じであることを保証するためだけの値)。古典RL(2色)は9,976ステップかかり寿命内に届かない |
| 盤面 | **v4: 60列 × 120行、左右ラップ(`WRAP_HORIZONTAL`)、上下は場外(`WRAP_VERTICAL=false`)。攻撃軸は上下** | 盤面を90度回転し、ラップ軸と攻撃軸を入れ替えた。得点ライン `SCORE_LINE_Y = HEIGHT - ZONE_DEPTH = 104` | v3.1: 120列 × 60行、上下ラップ、左右が攻撃軸。得点までの横断距離は89〜104列、ハイウェイ1列あたり18ステップで最短1,602ステップ(実測到達中央値1,743)という見積りは**旧向きでの実測**であり、v4(縦方向・可変ルール)では未再測定([spec.md](spec.md)「未決定事項」) |
| 配置可能域 | 自陣の外端16行のみ(`ZONE_DEPTH=16`。side1: `y=0..15` / side2: `y=104..119`) | アリが盤面をほぼ横断しないと得点できない＝ハイウェイが必須になる | 自陣全体(短い距離で届いてしまい、ハイウェイが要らなくなる) |
| 得点条件 | 敵の配置可能帯に到達で1点 | 単純で分かりやすい | 帯を突破して奥の端まで(防御ブロックが効くようになるが、妨害アリを採用したので不要) |
| **「ハイウェイ以外を落とす」仕組み** | **アリの寿命(最大ステップ数)** | カオス的運動は正味変位がほぼゼロなので、距離の制約がそのままフィルタになる。実測で、寿命の余裕を1.05〜2.5倍に変えても得点弾のHW割合は98%で不変(=非HWは寿命を緩めても届かない) | 明示的なハイウェイ判定を実装して弾く(複雑で、ルールとして説明しづらい) |
| **防御手段** | **安価な妨害アリ(コスト3・寿命400)** | 実測で、配置ブロックによる防御はまったく効かない(80個置いても得点率が下がらない)。一方、狙って撃った妨害アリは98%の確率で攻撃を止める | 配置ブロックで防ぐ(実測で機能しない) / 得点条件を「帯の突破」にする(機能するが、駆け引きが静的) |
| **テンプレートの評価** | **妨害込みで評価し、攻撃と妨害を共進化させる** | 空盤面だけの評価だと「妨害に強い配置」を選べず、攻撃側が探索すれば**14秒で無敵の弾**が作れてしまう(実測)。交互に回せば健全な均衡に収束する | 空盤面のみで評価(勝ち確定の弾が生まれる) / 攻撃だけ妨害込み評価(防御が追いつけない) |
| **テンプレート数** | **攻撃9種・妨害9種**(候補プールから選抜) | 人が一覧を把握して選べる数。9種なら**発射位置・向きで一意に識別できる**ので「相手が何を撃ったか読んで対応する」ゲームになる。実測でバランスの取れた9×9(止められない攻撃0件・死に札0件)を構成できた | 多数のテンプレート(識別できず読み合いにならない) / 自由入力のみ(良配置が上位0.1%で人間には無理) |
| **防御が決定論的になる問題** | **護衛(自分の妨害アリで相手の迎撃を壊す)** | 9種だと防御側が確実に識別・迎撃できてしまい膠着する。実測で、護衛を付けると突破率が0%→100%になり、その護衛付き攻撃にも新たな迎撃が必ず見つかる(6/6)。重ねるほどトークンを食うので読み合いが成立する | 迎撃コストを上げる(単調な数値調整で読み合いが増えない) / 識別を難しくする(9種に絞った意味が消える) |
| 同時飛行 | 1陣営最大4匹 | 妨害が強すぎる(1対1では通過率2%)ため、多重攻撃で飽和させる余地が要る。実測で攻撃2 vs 妨害1 なら46%通過 | 1匹のみ(防御が一方的に強くなる) |
| 盤面のクリーンアップ | `lastToucher` が一致するマスと自分の配置マスだけを白に戻す | 複数アリが同じマスを踏み合うため、単純な一括クリアだと他のアリの軌跡を壊す | 一括クリア(他のアリの状態が壊れる) / クリアしない(汚れが蓄積し予測値が無意味になる) |
| 陣営の座標系 | side1 ローカル座標に正規化し、side2 は `yGlobal = HEIGHT - 1 - yLocal` で鏡像変換(x は共有トーラス軸なので変換しない、向きは up⇄down を入れ替え) | テンプレート集を1つだけ持てばよく、エンジンも片側分のロジックで済む | 陣営ごとに別生成(生成時間もファイルサイズも倍) |
| CPUの構成 | **戦術=事前計算テーブル / 戦略=自己対戦で学習** | 9種しかないので「どの札がどの札に勝つか」は全ペア総当たりで事前計算できる(カウンター表・護衛表)。残る判断は「いつ何にトークンを使うか」だけで、パラメータ13個の小さな方策になる | 全部を学習させる(状態空間が無駄に大きい) / 全部を手書きヒューリスティックにする(調整が終わらない) |
| CPUの学習手法 | CEM法(交差エントロピー法)による自己対戦 | パラメータ13個なので勾配不要。実測で **362試合/秒**、集団60×40試合×40世代 = **約4分** | 強化学習(この規模では過剰。Phase 2) |
| ホスティング | GitHub Pages(静的配信) | ビルド不要・無料・要件を満たす | サーバーサイド構成(この規模では過剰) |
| ランタイム構成 | ビルドツール無しの素のJS + Canvas | 静的配信に合致し、依存管理の手間がない | React 等の導入(過剰) |
| Web Worker | 不採用 | 実行時はテーブル参照のみで軽量。実測で1アリ1ステップあたり0.001ms未満 | 採用(実行時にオンライン探索する設計を選んだ場合は必要) |
| シミュレーションコードの置き場所 | `src/engine.js` を DOM 非依存の純粋な JS にし、Node(生成・学習・検証)とブラウザ(実行時・先読み)の両方から共有 | 二重実装によるズレを防ぐ | Node用とブラウザ用で別実装(ズレのリスク) |

`src/cpu.js` から `src/engine.js` のシミュレーション関数を呼ばないという制約は、コード上で確認済み(`src/cpu.js` は `engine.js` を一切 import しない)。実行時にオンライン探索をしない設計を、コード上の依存関係で担保している([AGENTS.md](../AGENTS.md) の Do NOT)。

## テンプレート生成パイプライン(方針: MAP-Elites 版)

`scripts/generate-templates.mjs` は**パイプライン制御のみ**を担当し、探索そのものは `src/search/` に委ねる、というのが v4 の方針。想定するステージ順:

```
ランダム種 genome → MAP-Elites 探索(第1アーカイブ: ハイウェイ発見)
  → ハイウェイアーカイブ(direction × speed × formationTime)
  → ゲーム射影(第2アーカイブ: costTier × entryPositionTier × robustnessTier)
  → 攻撃/妨害それぞれの MAP-Elites 探索
  → 共進化(攻撃ラウンド/防御ラウンドを交互)
  → 候補プール
  → 9×9 選抜
```

> ⚠️ **これは方針であり、現状のコードそのものではない。** 本稿執筆時点の `scripts/generate-templates.mjs` は `src/search/*` を import しておらず、上記ステージには沿っていない。代わりに乱数候補(`blob()` によるランダムな塊配置)を直接生成し、`simulateSolo`/`simulateVersus` で共進化させる v3.1 由来のロジックがそのまま残っている(下の「データの流れ」節はこの**現行の**実装を説明する)。加えて `scripts/generate-templates.mjs` は存在しない設定値 `C.RULE` と `C.HIGHWAY_COLUMNS_PER_STEP` を参照しており(`src/config.js` には無い)、`blob()` は `WRAP_VERTICAL=false` にもかかわらず y 座標を `% C.HEIGHT` でラップしている。実行すれば `rule: undefined` を含む `templates.json` が書き出される可能性が高く、v4 の盤面・ルール設計とは矛盾した状態にある。テンプレート生成ロジックに手を入れる前に、この移行作業自体が必要。

## データの流れ(現行の `scripts/generate-templates.mjs`)

**段階1(生成)** — `scripts/generate-templates.mjs`

1. 配置可能帯の中で初期配置候補を生成し、`src/engine.js` でシミュレーションしてスコアリング
2. **共進化ループ**を交互に回す(実測で4ラウンド・約2分で収束)
   - 攻撃ラウンド: 各攻撃を「現在の妨害集 × 発射タイミング」の総当たりで評価し、**止められる組み合わせが少なくなる方向**へ変異させる
   - 防御ラウンド: カウンターを1つも持たない攻撃を見つけ、それを止められる妨害を探索して妨害集に追加する
3. 攻撃60件・妨害80件程度の候補プールを得る

**段階2(選抜)**

4. 候補プール全体のカウンター行列(攻撃 × 妨害 × 発射タイミング)を計算する(実測: 60×80 で1秒)
5. [spec.md](spec.md) の選抜基準を満たす **9×9** を貪欲法+局所探索で選ぶ

**段階3(組み込み)**

6. 選んだ9+9と、`counterTable` / `escortTable` / `identifyTable` を `data/templates.json` に書き出してコミット

**方策学習・検証**

7. `scripts/train-policy.mjs` が `templates.json` を使ってCPU同士を自己対戦させ、方策パラメータ(発射閾値・防御バイアス・時間重み)をCEM法で学習して `data/policy.json` に出力
5. `scripts/simulate-matches.mjs` が学習済み方策同士を大量に対戦させ、バランス指標(得点率・HW割合・盤面汚染度など)を出力
6. ブラウザ実行時、`src/app.js` が両JSONを読み込み、プレイヤーには攻撃/妨害のタブで9種ずつ一覧提示、`src/cpu.js` は方策に従って選択(実行時の再シミュレーションは行わない)
7. `src/engine.js` は実行時、試合の進行にのみ使う。MVP では自由入力が無いので**先読みシミュレーションは不要**(テンプレートの予測値はすべて `templates.json` の事前計算値)。Phase 2 で自由入力を入れるときに先読みが要る

## 干渉とテンプレートの予測値

v2 では両陣営が干渉しない設計だったが、v3 では**干渉こそが駆け引きの中心**になった。したがってテンプレートの予測値(到達時間・到達距離)は**空盤面での値**であり、実戦では相手の妨害や自軍の他のアリによってズレる。これは仕様であり、UI では「予測値」であることが分かる表示にする。

> ⚠️ 以下の実測値(干渉の強さ・共進化の収束・オフライン処理の所要時間)はいずれも **v3.1(RRL固定・120列×60行・上下ラップ)で計測したもの**。v4(rule/colorCount がテンプレートごとに可変・60列×120行・左右ラップ)では未再測定(`src/config.js` の `BALANCE` コメント、[spec.md](spec.md)「未決定事項」参照)。テンプレート再生成後に実測して更新すること。

実測された干渉の強さ(v3.1):

| 状況 | 攻撃の通過率 |
|---|---|
| 攻撃1発のみ | 100%(定義上、得点する弾を選んでいるため) |
| 攻撃1発 vs 乱数で撃った妨害1発 | 97%(＝乱数妨害はほぼ効かない) |
| 攻撃1発 vs 狙って撃った妨害1発 | **2%**(＝98%阻止。攻撃テンプレート30件すべてについて、400回の探索でカウンターが見つかった) |
| 攻撃2発 vs 狙って撃った妨害1発 | 46% |
| 攻撃3発のみ(妨害なし) | 59%(＝**攻撃どうしも干渉する**) |

### 共進化の収束(実測v3.1・妨害手札100種 × タイミング10通り = 1,000通り)

| ラウンド | カウンター数(最小/中央/最大) | カウンターを持たない攻撃 |
|---|---|---|
| 0(乱数の手札) | 2 / 36 / 50 | 0/16件 |
| 1(攻撃が最適化) | 1 / **7** / 30 | 0/16件 |
| 2 | 2 / 13 / 33 | 0/16件 |
| 3 | 2 / 12 / 27 | 0/16件 |
| 4 | 1 / **10** / 21 | 0/16件 |

攻撃側の最適化でカウンター密度が **3.6% → 1.0%** に下がり、以後は安定します。**カウンターを1つも持たない攻撃は最後まで出ません**。所要108秒。

## オフライン処理の所要時間(実測・v3.1)

> ⚠️ 下表は盤面 120×60・RRL固定 のときの実測値。v4(60×120・rule可変)でのスループットは未計測。

| 処理 | 実測値(v3.1) |
|---|---|
| シミュレーション評価のスループット(120×60・寿命2,400) | 約 16,500 回/秒(Node.js 単スレッド) |
| テンプレート生成 200万評価 | 約 2分 |
| テンプレート生成 1000万評価 | 約 10分 |
| 妨害込みの1件評価(妨害100種 × タイミング10通り) | 約 12ms |
| カウンター行列の計算(攻撃60 × 妨害80 × タイミング10) | 約 1秒 |
| **1試合のシミュレーション(120×60・240秒・最大8匹)** | **約 2.8ms(362試合/秒)** |
| 方策学習(CEM・集団60 × 40試合 × 40世代) | 約 4分 |
| バランス検証 5,000試合 | 約 14秒 |
| 共進化4ラウンド(攻撃16件 × 妨害100種) | 約 108秒 |
| 方策学習(CEM法・40世代・9.6万試合) | 数秒〜数十秒 |

**いずれも数分以内で完結する。** 並列化(`worker_threads`)は不要だが、必要なら評価が独立なので容易に効く。
