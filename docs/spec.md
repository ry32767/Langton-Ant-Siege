## 2. ゲームルール(全機能の前提)

実装前にここを読むこと。数値は `src/config.js` に一元化し、ハードコードしない。

### 盤面

```
        x=0                                                    256
   y=0  ┌───────────────────────────────────────────────────────┐
        │ side1 配置可能帯                                        │ y=0..31    ＝side2の得点目標
  y=32  ├───────────────────────────────────────────────────────┤
        │                                                       │
        │            中間地帯(配置不可)                           │ y=32..223(192行)  幅256・左右ラップ
        │                       │                               │
        │                       ▼ side1 のアリ                    │
 y=224  ├──────┬─────────────────────────────────┬──────────────┤
        │ 壁32列│      得点ゲート(中央192列)         │  壁32列       │ x<32 または x≥224 は得点ゲートの外
        │ side2 配置可能帯                                        │ y=224..255 ＝side1の得点目標
 y=255  └───────────────────────────────────────────────────────┘
        ゲート内(32<=x<224)に到達で1得点。ゲート外に到達した場合は得点せず消滅
```

| 項目 | 値 | 備考 |
|---|---|---|
| 盤面 | **256列 × 256行(正方形)** | **左右はラップ(トーラス)。上下の端に出たアリは消滅** |
| 配置可能帯の深さ | **32行**(`ZONE_DEPTH`) | side1 は y=0..31、side2 は y=224..255 |
| 中間地帯 | y=32..223(192行) | どちらも配置できない |
| **得点条件** | **敵の配置可能帯に到達**(side1 なら y≥224=`SCORE_LINE_Y`)、かつそのときの x が**得点ゲート**の内側(下記) | 到達で **1得点**。先に5得点で勝ち |
| **得点ゲート** | 盤面中央の192列(`SCORE_GATE_X_MIN`=32 以上 `SCORE_GATE_X_MAX`=224 未満) | ゲートの外(左右32列ずつの「壁」)に到達した場合は**得点せず消滅**する。詳細は[得点ゲート](#得点ゲートv5)を参照 |
| ステップ速度 | 300 ステップ/秒 | 論理は固定ステップ、描画は requestAnimationFrame。v4(120ステップ/秒)から引き上げた。理由は下記「アリの種類と寿命」参照 |
| トークン | 毎秒 +1、上限 30 | アリ飛行中も蓄積する |
| 試合時間上限 | 240秒 | 時間切れ時は得点が多い方の勝ち。同点なら引き分け。`TOTAL_STEPS` = 240 × 300 = **72,000** |
| 同時飛行数 | 1陣営につき最大4匹 | 攻撃・妨害の区別なく合計4匹 |
| テンプレート数 | **攻撃9種・妨害9種** | 人が把握して選べる数に絞る。生成した候補プールから選抜する |
| 発射列 | **可変**(`antX`。発射時に選ぶ) | 詳細は[発射列の可変化](#発射列antXの可変化v5)を参照 |

### アリの移動規則(テンプレートごとの一般化ルール)

**グローバルなルールは存在しない。** 各テンプレート(＝そこから発射されるアリ)が自分のルールを持つ。

| 項目 | 規則 |
|---|---|
| `rule` | `'L'` / `'R'` だけからなる文字列。添字がセルの状態 |
| `colorCount` | `rule.length` と等しい。**2 ≤ colorCount ≤ 16** |
| ルールの変更 | 発射時にテンプレートから設定し、**そのアリが消滅するまで変更しない** |
| ルール長のコスト | **課さない**。コストは `baseCost + 配置セル数` のみ |

例: `rule = 'RLLRRLR'`(7色) なら、状態0で右・状態1で左・状態2で左・状態3で右…と回る。

1ステップの手順は次の順で行う。

1. **今乗っているマスの生値を読み、自分の色数で割った余りを状態とする**(下の[異種ルールの衝突](#異種ルールの衝突共通ルール))
2. **その状態**で回転を決める(`rule[状態]`)
3. マスの状態を1つ進める(`(状態 + 1) % colorCount`)
4. 向いている方向へ1マス前進する(**左右はラップ、上下はラップしない**)
5. 前進した結果で消滅・得点を判定する(下の[得点判定](#得点判定と盤面のクリーンアップ))

> ⚠️ **回転は「進める前の状態」で決める。** 進めた後の状態で判定すると別のセルオートマトンになり、ハイウェイの形成ステップも軌道もすべて変わる。参照実装(`src/engine.js` の `stepAnt`):
> ```js
> const raw = board[j];
> const s = raw % ant.colorCount;
> ant.dir = ant.rule[s] === 'R' ? (ant.dir + 1) & 3 : (ant.dir + 3) & 3;
> board[j] = (s + 1) % ant.colorCount;
> ```

### 異種ルールの衝突(共通ルール)

盤面は1枚を全アリで共有するが、色数はアリごとに違う。だから**ルールにない色を踏む**ことが起こる。
これを次の1行で吸収する。

```js
const s = board[i] % ant.colorCount;
```

例: 16色のアリが状態 `13` を残したセルに3色のアリが入ると、`13 % 3 = 1` として**状態1と解釈**し、その後 `1 → 2` へ書き換える。

> **この状態空間の圧縮そのものをゲーム上の干渉として扱う。** 色数の少ないアリは相手の高い状態値を踏み潰し、色数の多いアリは相手の軌跡を自分の広い状態空間で読む。ルール長の選択が干渉の非対称性として効いてくる。

### 得点ゲート(v5)

敵陣(side1 なら y≥`SCORE_LINE_Y`=224)に**到達しただけでは得点にならない**。到達した瞬間の x が盤面中央192列(`SCORE_GATE_X_MIN`=32 以上 `SCORE_GATE_X_MAX`=224 未満)の中に入っているときだけ1得点で、外に出た場合は**得点せず消滅**する。ゲートの外側(左右32列ずつ)は「壁」になる。

```js
// src/config.js の isInScoreGate()。engine の得点判定と UI の描画が共有する唯一の定義
export function isInScoreGate(x) {
  return x >= SCORE_GATE_X_MIN && x < SCORE_GATE_X_MAX;
}
```

⚠️ **盤面を256列に広げ、かつ発射列を可変にした**([発射列の可変化](#発射列antXの可変化v5)参照)ことの帰結として、守る側は256列すべてを警戒しなければならず迎撃が成立しなくなる。得点を中央192列に限ることで「門を守る」という防衛目標を作り、`attacksWithoutCounter = 0`(必須条件)を満たせる幅に戻す。

x はグローバル座標のまま両陣営で共通に判定できる(x は陣営間で鏡像にならない。鏡像になるのは y だけ)。

### 発射列(antX)の可変化(v5)

**テンプレートは発射列 `antX` を持たない。** 配置マス(`cells`)は**アリからの相対座標** `[dx, dy, state]` で持ち、プレイヤー/CPU が発射時に `antX`(0..255 の任意の列)を自由に選ぶ。

根拠: **左右がトーラスなので、x方向の平行移動は力学の厳密な対称性である。** 同じテンプレートをどの列から撃っても、軌道は平行移動するだけで形・周期・並進・形成ステップは変わらない。一方 `antY`(発射行)はテンプレート固有のまま変えられない — y方向の平行移動は得点ラインまでの距離を変え、寿命内に届くかどうかに影響するため。

帰結:

- `identifyTable` のキーは `"antX,antY,antDir"` → **`"antY,antDir"`** になった。攻撃9種が発射「行」と向きの組だけで識別できることが選抜の必須条件
- `counterTable[攻撃ID]` の各要素は `{ disruptId, deltaX, fireAtStep, successRate }`。`escortTable[攻撃ID][迎撃妨害ID]` の各要素は `{ interceptDeltaX, interceptFireAtStep, escortDisruptId, escortDeltaX, fireAtStep }`。`deltaX` は「妨害の発射列 − 攻撃の発射列」を `WIDTH` で割った余りで、絶対列ではなく**差分**の表になる
- 攻撃テンプレートは `entryXAt0`(発射列0で撃ったときに敵陣へ入る列)を持つ。実プレイでの到達列は `(antX + entryXAt0) mod WIDTH`。したがって「得点したいなら撃てる列は幅192列の連続区間(トーラス上)に限られる」という新しい駆け引きが生まれる(`src/template.js` の `scoringLaunchColumns` / `launchColumnScores` が計算する)
- 探索・カウンター表計算では `deltaX` を掃引するコストが生じる。共進化の途中は `COEVO_DELTA_X_STRIDE`(=16)の粗いグリッドで近似し、最終9×9のテーブル計算だけ全256列を掃引する(`scripts/generate-templates.mjs`)

### ハイウェイについて(実測)

ハイウェイの向きは**ルールでも初期配置でも変えられない**。ルール長2〜6の全114ルール × ランダム初期配置200通り(計22,800試行)で検出された3,520件のハイウェイは、**すべて並進ベクトルが (±1, ±1) の45度**だった。4方向の違いは**発射時の向き**から来る。

ルール長を2〜16へ、配置セルの状態を自由にまで広げると45度以外も現れるが、極めて希少(検出7,680件中13件・0.17%)。

したがって**ルール選択が効くのは向きではなく速度・形成ステップ・色数**である。

| ルール | 色数 | 周期 | 行/ステップ | 形成ステップ |
|---|---|---|---|---|
| `RRL` / `LLR` | 3 | 18 | **0.0556** | 38 |
| `RRRRL` / `LLLLR` | 5 | 68 | 0.0294 | 102 |
| `RRRLLL` / `LLLRRR` | 6 | 38 | 0.0263 | 98 |
| `RRRRRL` / `LLLLLR` | 6 | 84 | 0.0238 | 126 |
| `RL` / `LR`(古典) | 2 | 104 | 0.0192 | **9,976**(寿命外) |

> 上表の周期・速度・形成ステップは**セルオートマトンのルールだけで決まる CA 固有の値**で盤面サイズに依存しないため、v4 実測のまま有効(単位を「列」から「行」に修正しただけ)。一方、下の「左右がラップするので〜」の得点率・到達ステップは**盤面サイズと寿命に依存する v3.1(120×60・寿命2,400)実測**であり、v5(256×256・寿命6,000)では未再測定。
>
> 🚧 **未測定(本探索後に埋める)**: v5 盤面(256×256)でのランダム genome の得点率・到達ステップ分布。

`C.LEGACY_RULE`(=`'RRL'`)は**回帰フィクスチャ専用**の定数で、既定ルールではない。

### アリの種類と寿命

| 種類 | コスト | 寿命(最大ステップ) | 用途 |
|---|---|---|---|
| **攻撃アリ** | 5 + 配置マス数 | **6,000**(20秒。🚧 暫定値。下記参照) | 敵の配置可能帯まで届く |
| **妨害アリ** | 3 + 配置マス数 | **1,000**(3.3秒) | 中間地帯までしか届かない。敵のアリの軌跡を壊す |

配置マスは1回の発射につき最大16個。攻撃アリのコストは 6〜21、妨害アリは 4〜19。

> 🚧 **`ATTACK_LIFE`(=6,000)は暫定値。** 本探索の結果から `scripts/tune-attack-life.mjs` で実測して確定させる(詳細は「[未決定事項](#9-未決定事項--要確認)」)。第1アーカイブ(ハイウェイ発見)は仮想盤面を `SEARCH_LIFE` まで走らせるので `ATTACK_LIFE` に依存しない。探索中のゲーム射影は `ATTACK_LIFE` ではなく `GAME_LIFE_SEARCH_CAP`(=12,000)で行い、個体ごとの**実到達ステップ数(`arrivalStep`)**を記録してあるので、寿命を変えても探索をやり直さずに再射影できる。
>
> 盤面が 60×120 → 256×256 になり、最深発射位置(y=`ZONE_DEPTH`-1=31)から得点ライン(y=224)までが**193行**になった(v4 は88行)。速度クラスごとの**必要ステップ数(導出値。実測ではない)**は次のとおり:
>
> | v_y(行/ステップ) | 必要ステップ | 到達可否(寿命6,000) |
> |---|---|---|
> | 0.0556(周期18・drift 1) | 3,471(11.6秒) | 届く |
> | 0.0385(周期52・drift 2) | 5,018(16.7秒) | 届く |
> | 0.0327(下限) | 5,900(19.7秒) | 届く |
> | 0.0294(周期34・drift 1) | 6,562(21.9秒) | **寿命6,000の外** |
>
> つまり `ZONE_DEPTH`=32 では最低速クラスが落ちる。到達可能な v_y は 0.033〜0.056 で、到達時間に 11.6〜19.7秒 の差が出る(v4 は 13.5〜28.7秒)。ここは読み合いの軸なので `ARCHIVE2.speedClassBins` をこの範囲に合わせて切り直してある。
>
> ⚠️ 「寿命がハイウェイ以外を落とすフィルタ」という設計原則は v4 同様に弱まっている。得点弾のハイウェイ割合(`highwayShareOfScoring` 95%以上)を必ず再測定して確認すること。

### 配置マスの書き込み(発射時の盤面操作)

検証スクリプト(`verify-v3/*.mjs` の `place()` / `matchbench.mjs`)で確定している挙動。実装はこれに合わせる。

| 項目 | 規則 |
|---|---|
| 書き込む状態 | **テンプレートが指定した状態**(`cells` の3要素目)。固定値ではない。制約は `0 ≤ state < rule.length` |
| 既に非白のマスと重なった場合 | **無条件で上書き**する(加算しない・配置不可にもしない) |
| 配置マスの下限 | **規則上は0個**(アリだけの発射も成立する)。ただし**テンプレート/genome は1個以上を必須**とする(下記) |
| アリの初期位置 | 自陣の配置可能帯の中(side1 なら x は発射時に自由に選べる0..255の任意の列、y=0..31)。**配置マスと重なってよい** |
| 配置マスの座標 | **v5: アリからの相対座標**(`[dx, dy, state]`)で持つ。アリの近傍(チェビシェフ半径 `TEMPLATE_CELL_RADIUS`=8)に限定される。配置帯全体(256×32=8,192マス)に一様に撒くと密度0.2%になりアリが配置マスを一度も踏まないため(v4 実測で判明) |
| 配置マス同士の重複 | **禁止**。同じ (dx, dy) に2つ置かない |
| 0マス発射の危険性 | アリ1匹だけでも敷いたハイウェイで得点できてしまい、しかも軌道が発射位置と向きだけで決まるので読み合いにならない。コスト最安の手なので、テンプレートに0マスのものを混ぜてはならない |
| 発射時の `lastToucher` | 置いた配置マスの `lastToucher` を**そのアリのIDで埋める**(-1 のままにしない)。他のアリが後から踏むとIDが上書きされ、そのマスはクリーンアップ対象から外れる |
| 発射したステップの扱い | 配置マスを書き込んだ**同じステップ内でそのアリも1歩進む**(次のステップまで待たない) |

### 得点判定と盤面のクリーンアップ

判定はすべて**前進した後**に、次の順で行う。

1. 前進先が自陣側の端の外(side1 なら y<0)なら消滅(得点なし)
2. 前進先が敵の配置可能帯(side1 なら y≥224=`SCORE_LINE_Y`)なら、そのときの x が[得点ゲート](#得点ゲートv5)の中かどうかを判定する。中なら陣営に **1得点**してアリは消滅、外なら得点せず消滅する
3. 上のどちらでもなく `steps >= life` になったら消滅(得点なし)

> 得点したマスの状態は書き換わらない(状態更新は前進**前**のマスに対して行うため)。したがって敵陣の帯は攻撃アリによって汚れない。
> 下端(y≥256)の場外判定は書かなくてよい。y≥224 で先に得点判定が入るため到達しない。
> **左右に場外は無い**(x はトーラス)。
> ⚠️ **`cleanupAnt` の性能修正(v5)**: 盤面が 7,200 → 65,536 マスになったため、消滅時の「`lastToucher` が自分と一致する全マス」を全盤面走査で探すと1試合あたり数十匹の消滅がボトルネックになる。`src/engine.js` は代わりに、アリが移動のたびに踏んだマスの添字を `ant.touched` に記録しておき、消滅時はそこだけを見る(結果は全盤面走査と同値。`test/engine.test.js` に回帰テストあり)。

アリ消滅時、次の2種類のマスを白(状態0)に戻す。

- その発射で置いた配置マスのうち、**他のアリが触れていないもの**
- そのアリが最後に触れたマス(`Cell.lastToucher` がそのアリと一致するマス)

> ⚠️ 複数のアリが同じマスを踏み合うため、**盤面は完全には元に戻らない**。これは意図した仕様で、干渉こそが本作の駆け引きの中心。ただし汚れが蓄積しすぎるとテンプレートの予測値が信用できなくなるため、`simulate-matches.mjs` で試合終盤の盤面汚染度を必ず計測する(下の[検証戦略](#6-検証戦略)参照)。

### 護衛(escort)

妨害アリは**自分の攻撃を守るためにも使える**。相手の迎撃アリが自分の攻撃の軌跡を壊しに来る前に、その経路へ自分の妨害アリを送り込めば、迎撃側の軌道が崩れて攻撃が生き残る。

新しい機能ではなく、**「妨害アリはどのアリの軌跡にも干渉する」という既存ルールの帰結**。ただしゲームの深さの中心なので明記し、CPU にも実装する。

実測(下の[検証戦略](#6-検証戦略)のバランス指標に反映):

| 状況 | 攻撃の突破率 |
|---|---|
| 攻撃のみ vs 有効な迎撃 | **0%**(必ず止まる) |
| 攻撃＋護衛 vs 同じ迎撃 | **100%**(護衛を200回探索した場合) |
| 護衛付き攻撃 vs 新たに探した迎撃 | 6件中6件で有効な迎撃が見つかる |

> ⚠️ この実測は `verify-v3/escort.mjs` が**発射順**にアリを動かして測った値で、本仕様のステップ順序(下の[共有盤面とステップ順序](#共有盤面とステップ順序)。陣営単位で、しかも手番が毎ステップ入れ替わる)とは食い違う。`src/engine.js` で再測定したとき 0%/100% がそのまま出なくても回帰ではない。合格ラインは下の[バランス指標](#バランス指標simulate-matchesmjs-の合格ライン)の「攻撃＋護衛 vs 同じ迎撃の突破率 60〜100%」で判定する。

**攻撃 → 迎撃 → 護衛 → 再迎撃** と重ねるほどトークンを消費するので、どこで降りるかの読み合いになる。

### 共有盤面とステップ順序

盤面は1枚を両陣営で共有する。1ステップの処理順は次で固定する。順序を固定しないと結果が再現しない。

1. **トークン加算**(`TOKEN_TICK_STEPS`=300ステップに1回。ステップ0でも加算するので、試合開始直後の保有は1)
2. **予約発射の反映**(`counterTable` / `escortTable` で記録した発射を `fireAtStep` ちょうどに実行する。配置マスの書き込みもここ)
3. **新しい判断**(`DECISION_INTERVAL_STEPS`=300ステップに1回)
4. **アリの移動**(先手の陣営 → 後手の陣営の順で、それぞれ発射順に全部移動)
5. **勝敗判定**(どちらかが5得点していたら終了)

#### 両陣営の判断は「同時」に行う

判断フェーズ(3)では、**先に両陣営の view を取得してから**、それぞれの `decide` を呼ぶ。逐次に処理すると、後に判断する側だけが「相手がこのステップで撃ったばかりのアリ」を view で見られてしまい、情報の非対称が生まれる。

実測: 逐次判断だと **先手勝率100%・平均得点 4.88 対 2.04**（攻撃の得点率が side1=28.7% 対 side2=14.8%）という露骨な偏りが出た。同時判断に変えたことで **先手勝率 50.4%**（3,000試合）に是正された。

#### 発射と移動の手番は1ステップごとに入れ替える

ステップ `s` での予約発射(2)と移動(4)の処理順は、**偶数ステップは side1 が先、奇数ステップは side2 が先**とする(`src/config.js` の `ALTERNATE_STEP_ORDER`)。同じ陣営が毎ステップ先に盤面へ書き込むのを避けるため。

> ⚠️ **注意**: 判断フェーズ(3)の手番を「ステップ番号 `s` の偶奇」で入れ替えてはいけない。判断は300ステップに1回しか走らず、300は偶数なので、ステップ番号の偶奇では**永久に同じ陣営が先**になる。判断フェーズは「判断が何回目か」(`floor(s / 300) % 2`)の偶奇で入れ替える。

**CPU の意思決定は300ステップに1回**(トークン加算と同じ周期。`DECISION_INTERVAL_STEPS`=`STEPS_PER_SECOND`)に固定する。実行時探索をしないので毎ステップ考える必要がなく、周期を固定しておくと自己対戦の結果が再現する。**プレイヤーの発射は押した次のステップで反映**する(待たせない)。

> ⚠️ **予約した発射は300の周期に縛られない。** `FIRE_TIMINGS` は `ATTACK_LIFE` から導出する(固定リストではない。`src/config.js` の `FIRE_TIMING_INTERVAL`/`FIRE_TIMING_LAST` 参照)。v5(`ATTACK_LIFE`=6,000)では間隔375(`STEPS_PER_SECOND * 1.25`)・終端4,500 で、`[0, 375, 750, ..., 4500]` の**13通り**になり、うち300の倍数は **0 / 1500 / 3000 / 4500 の4つ**だけ。「意思決定は300ステップ周期」だけを規則にすると、記録された `fireAtStep: 375` のような迎撃が**物理的に撃てなくなる**。したがって:
>
> - **新しい判断**(何を撃つか決める)は300ステップに1回
> - **その判断で予約した発射**(迎撃・護衛)は、記録された `fireAtStep` の**そのステップちょうど**に実行する
>
> 予約は決定論的なので再現性は保たれる。これを変える(例: `FIRE_TIMINGS` を300の倍数に丸める)場合、REVIEW.md 付録D/E のカウンター数・突破率は別のタイミング格子で測った値になるので、**テンプレートの再生成と再計測が必要**。
>
> ⚠️ `FIRE_TIMINGS` は `ATTACK_LIFE`(暫定値)から導出されるため、`ATTACK_LIFE` を実測で確定させたら `FIRE_TIMINGS` の件数・境界も自動で追随する(定数リテラルでは固定しない設計)。

> `verify-v3/matchbench.mjs` の `match()` がこの順序の参照実装。

### 陣営の座標系(ミラーリング)

**side1(上)** のローカル座標がグローバル座標。**side2(下)** は上下反転。

| 対象 | 変換 |
|---|---|
| x座標 | **変換しない**(`xGlobal = xLocal`) |
| y座標 | `yGlobal = 255 - yLocal`(= `HEIGHT - 1 - yLocal`) |
| 向き | `up ⇄ down` を入れ替える(`left` / `right` はそのまま) |

`data/templates.json` の座標・向きは**すべて side1 ローカル座標で保存**し、side2 が使うときに変換する。

### 乱数とシード

乱数は「CPUがテンプレート候補から1つ選ぶ」ところだけで使う。試合開始時にシードを決めて `Match.seed` に保持し、決定論的な擬似乱数(xorshift等)で進める。`scripts/simulate-matches.mjs` は `--seed <n>` でシードを固定でき、同じシードなら結果が完全に再現する。

## 3. 機能一覧

### ✅ MVP

#### 機能1：アリ・シミュレーションエンジン(RRL)
- [ ] 状態0または1のマスにいる時、状態を1つ進め、右に90度回転してから1マス前進する
- [ ] 状態2のマスにいる時、状態を0に戻し、左に90度回転してから1マス前進する
- [ ] 盤面の**左右**端を越えた移動は反対側の端に回り込む(トーラス。x=-1→x=255、x=256→x=0)
- [ ] **上**の端(y<0)を越えたアリは消滅し、得点は発生しない(下端は y≥224 で先に得点判定が入るため到達しない)
- [ ] 任意のルール(`RL` / `RRL` / 16色ルール)を指定でき、それぞれ指定どおりに回転する
- [ ] ルールにない色を踏んだとき、`board[i] % colorCount` として解釈される(状態13のマスに3色アリを置くと状態1として動く)
- [ ] 異なる色数のアリを同じ盤面で同時に走らせられる
- [ ] 寿命(攻撃6,000 / 妨害1,000ステップ)を使い切ったアリは消滅し、得点は発生しない
- [ ] 空盤面でアリを走らせると **38ステップ目からハイウェイ状態**(周期18で毎回同じ斜め1マスの並進)になる(`LEGACY_RULE` の回帰フィクスチャ。盤面サイズに依存しない CA 固有の値)
- [ ] 敵陣(y≥224)に到達しても、そのときの x が得点ゲート(32≤x<224)の外なら得点にならず消滅する

#### 機能2：準備フェーズ(資源トークン)
- [ ] 試合開始と同時に両陣営のトークンが0からスタートし、1秒ごとに+1される
- [ ] トークンは上限30で頭打ちになり、それ以上は蓄積されない
- [ ] アリ飛行中もトークンは蓄積される
- [ ] 配置マスは自陣の配置可能帯(side1 なら y=0..31)にのみ置け、y=32 以降には置けない
- [ ] 配置マスは指定された状態(`[dx, dy, state]` の3要素目)で書き込まれる
- [ ] 配置マスは1回の発射につき最大16個まで
- [ ] 発射コストは「攻撃アリ 5 / 妨害アリ 3」＋配置マス数
- [ ] 保有トークンがコスト未満のとき、発射ボタンが無効化されて押せない
- [ ] 自陣のアリが4匹飛行中のとき、発射ボタンが無効化されて押せない
- [ ] 発射時、コスト分のトークンが消費される
- [ ] プレイヤー/CPU は発射時に発射列(`antX`。0..255)を自由に選べる

#### 機能3：テンプレート選択(9種 + 9種)
- [ ] 攻撃9種・妨害9種のテンプレートがタブで分かれて一覧表示される
- [ ] 攻撃テンプレートには **コスト・到達時間(秒)・カウンター数**(9種の妨害のうち何種で止められるか)が表示される
- [ ] 妨害テンプレートには **コスト・到達距離(行)・カバー数**(9種の攻撃のうち何種を止められるか)が表示される
- [ ] 保有トークンがコスト未満のテンプレートはグレーアウトされ、クリックしても選択されない
- [ ] テンプレートを選ぶと、選んだ発射列(`antX`)に応じて配置マスとアリの位置・向きが盤面上にプレビュー表示される
- [ ] 飛行中の敵の攻撃アリには**どのテンプレートか(A1〜A9)が表示される**(発射行(`antY`)と向きで一意に識別できる。`identifyTable` のキーは `"antY,antDir"`)
- [ ] 敵の攻撃を選択すると、それを止められる妨害テンプレートと推奨発射列(`deltaX`)・推奨発射タイミングが強調表示される

> **自由入力(テンプレート以外の配置)は MVP では実装しない。** 理由は3つ。①9種に絞ったからこそ「相手が何を撃ったか」を識別して読み合いができる。自由入力を許すと識別が成立しない。②実測では良い配置は乱数探索で上位0.1%以下なので、プレイヤーが自力で有効な弾を作るのは事実上不可能で、トークンを捨てるだけになる。③UIが複雑になる。Phase 2 で「識別されない代わりに性能も読めない上級者向けの弾」として検討する。

#### 機能4：発射と得点判定
- [ ] 発射ボタン押下で、下書きの配置マスとアリが自陣の配置可能帯に設置され、そのアリのシミュレーションが開始する
- [ ] アリが敵の配置可能帯(side1 なら y≥224)に入り、かつそのときの x が得点ゲート(32≤x<224)の中である瞬間、その陣営に1得点が入りアリが消滅する
- [ ] アリが敵の配置可能帯に入ったが x が得点ゲートの外(壁)だった場合、得点は発生せずアリが消滅する
- [ ] アリが自陣側の端を越えた場合(side1 なら y<0)、得点は発生せずアリが消滅する(敵側の端に出る前に得点判定が入るため、そちらは発生しない)
- [ ] アリが寿命を使い切った場合、得点は発生せずアリが消滅する
- [ ] アリ消滅時、「その発射で置いた配置マスのうち他のアリが触れていないもの」と「`lastToucher` がそのアリと一致するマス」を状態0に戻す
- [ ] 他のアリが踏んだマスは、そのアリの消滅時に消えずに残る

#### 機能5：妨害
- [ ] 妨害アリは攻撃アリと同じルールで動き、寿命だけが短い(1,000ステップ)
- [ ] 妨害アリも攻撃アリと同じ得点判定ロジックを通る(種類による特別扱いのコードを書かない)。ただし寿命1,000では最大でも約56行(1,000 × 0.0556)しか進めないため、192行ある中間地帯の1/3までしか届かず、敵陣(y≥224)には**到達しない**
- [ ] 飛行中の敵のアリの軌跡を妨害アリが踏むと、そのマスの状態が変わり、敵のアリのその後の軌道が変化する
- [ ] 妨害アリ自身も相手の軌跡の影響を受ける(特別扱いはしない)

#### 機能6：CPU AI(事前計算テーブル ＋ 自己対戦で学習した方策)

CPUは**戦術(どの札がどの札に勝つか)を事前計算のテーブルで持ち、戦略(いつ何にトークンを使うか)を自己対戦で学習する**。実行時の探索はしない。

**事前計算テーブル**(`data/templates.json` に同梱)

| テーブル | 内容 |
|---|---|
| `counterTable[攻撃ID]` | その攻撃を止められる `{disruptId, deltaX, fireAtStep, successRate}` の一覧。`deltaX` は「妨害の発射列−攻撃の発射列」の余り(v5) |
| `escortTable[攻撃ID][迎撃妨害ID]` | その迎撃を無効化できる `{interceptDeltaX, interceptFireAtStep, escortDisruptId, escortDeltaX, fireAtStep}` の一覧(v5) |
| `identifyTable` | 発射行(`antY`)・向き → 攻撃ID(**v5: キーは `"antY,antDir"`**。発射列 `antX` は可変になったため識別に使えない。9種は `antY`・向きの組がすべて異なるので1ステップで一意に決まる) |

**受け入れ条件**

- [ ] `data/templates.json` と `data/policy.json` を試合開始前に読み込む
- [ ] `src/cpu.js` は `src/engine.js` のシミュレーション関数を一切呼ばない(実行時探索をしないことをコード上の依存関係で担保する)。テンプレートの座標変換(相対→絶対)は `src/template.js` を使う(`engine.js` を経由しない)
- [ ] 敵の攻撃アリが出現したら、その発射行(`antY`)・向きから `identifyTable` を引いて**攻撃IDを特定する**
- [ ] 迎撃を選ぶときは `counterTable[特定した攻撃ID]` から選び、記録された `deltaX` で発射列を決め、記録された発射ステップで撃つ
- [ ] 自分の攻撃に対して敵の迎撃が飛来したら、`escortTable` を引いて護衛を撃てる
- [ ] 各判断(攻撃 / 迎撃 / 護衛 / 待機)は `policy.json` の方策パラメータに従う(下表)
- [ ] 発射できるテンプレートが1件も無い、または方策が待機を選んだ間は、トークンを貯め続ける
- [ ] 選択に乱数を使う箇所は `Match.seed` の擬似乱数を使い、同じシードなら同じ試合になる

**学習する方策パラメータ**(`data/policy.json`)

| パラメータ | 意味 |
|---|---|
| `fireThreshold` | このトークン数以上でのみ発射を検討する |
| `reserveTokens` | 迎撃用に温存しておくトークン量(これを下回る攻撃はしない) |
| `defendBias` | 敵の攻撃が飛来中に、攻撃ではなく迎撃を選ぶ確率 |
| `escortBias` | 自分の攻撃に敵の迎撃が来たとき、護衛を撃つ確率 |
| `attackPref[9]` | 9種の攻撃テンプレートの選好重み(softmaxで選択) |

**学習方法**: CPU同士の自己対戦 + CEM法(交差エントロピー法)。集団60・エリート12・各個体40試合・40世代。パラメータは13個なので勾配不要。実測で **362試合/秒**、1世代7秒、**40世代で約4分**。

#### 機能7：勝敗判定
- [ ] どちらかが5得点した時点で試合が終了し、勝敗を示す結果オーバーレイが表示される
- [ ] 240秒経過時点で決着していない場合、得点が多い方の勝ちとして試合が終了する
- [ ] 240秒経過時点で得点が同数の場合は引き分けとして終了する
- [ ] 結果オーバーレイには「もう一度対戦する」ボタンがあり、押すと初期状態から再スタートする

#### 機能8：対戦モード選択

#### 機能9：ハイウェイ探索(オフライン。v5 で追加)

`scripts/generate-templates.mjs` が実行するテンプレート生成パイプラインの一部。プレイヤー・CPU の実行時ロジックではなく、`data/templates.json` を作るための開発時処理。

**ハイウェイ検出の2段構え**

- [ ] 高速フィルタ(`src/search/highway-trajectory.js` の `detectHighwayFromPath`)が、軌跡(位置+向き)だけから周期性を検出する。MAP-Elites 探索中の全候補にこれだけを適用する
- [ ] 厳密確認(`src/search/highway-fingerprint.js` の `verifyHighwayStrict`)が、アリ座標を原点とした近傍セルの正規化 fingerprint を用いて、高速フィルタで採用された候補だけを盤面込みで再検証する
- [ ] `highway.trajectoryPeriodic` と `highway.fingerprintVerified` は独立した2つの boolean で、MAP-Elites 探索中(アーカイブ挿入・記述子計算)は前者だけを、最終テンプレート選抜(9×9)は後者だけを使う。混同しない
- [ ] `src/search/highway-detector.js` はこの2モジュールを再エクスポートするだけのファサードである

**Seed Distillation**(§10〜§24 相当)

- [ ] 検出済みハイウェイについて、形成時点(`formationStep` およびその後の安定周期開始位置)の局所盤面を crop 半径を段階的に広げながら切り出す(`src/search/seed-distillation.js` の `captureFormationSnapshot`)
- [ ] 切り出した種セルから走らせ直し(replay)、元のハイウェイと同じ `period`/`driftX`/`driftY` を `HIGHWAY_MIN_CYCLES`(5)周期以上再現することを確認する(`replaySeed`)。再現しなければその crop 半径・snapshot 位置を棄却する
- [ ] 再現した種セルを、アリから遠い順に貪欲削除して圧縮する(`src/search/seed-compression.js` の `compressSeed`)。削除後も再現性が保たれる場合のみ削除を確定する
- [ ] 圧縮後の種がゲームで採用可能かを判定する(`gameUsability`)。条件: セル数 ≤ `MAX_CELLS`(16)、`|dx|`/`|dy|` ≤ `TEMPLATE_CELL_RADIUS`(8)、かつ dy の広がりが `ZONE_DEPTH` に収まる `antY` が存在すること
- [ ] 採用可能な蒸留 genome(`origin: 'distilled'`)は、通常の genome と同じ扱いで MAP-Elites の第1アーカイブへ再投入される(特別扱いしない)
- [ ] 蒸留の試行数・成功数・成功率・formationStep 短縮量・セル数の変化・蒸留前後の viable 件数が `data/search-report.json` に記録される(`src/search/search-report.js` の `buildSearchReport`)

**並列化と決定論**

- [ ] `scripts/generate-templates.mjs` は `scripts/lib/worker-pool.mjs`(`worker_threads` の固定サイズプール)を使って genome の評価を並列化する
- [ ] 乱数(genome 生成・親選択・突然変異)は**メインスレッドだけ**が持ち、ワーカー(`scripts/lib/search-worker.mjs`)は渡された genome を評価して返すだけの純粋関数である
- [ ] 評価結果は**完了順ではなく投入した添字順**にアーカイブへ挿入される。この2条件を満たす限り、ワーカー数(`--workers`)を変えても `--seed` 固定なら出力がバイト単位で一致する

### テンプレート選抜基準(`generate-templates.mjs` 段階2の合格ライン)

9×9 を選ぶときの必須条件と目標。v4(60×120盤面)ではこれを満たす組み合わせが存在することを確認済み。v5(256×256盤面)は 🚧 未測定(本探索後に埋める)。

| 基準 | 値 | 種別 |
|---|---|---|
| カウンターを1つも持たない攻撃 | **0件** | 必須(1件でもあれば勝ち確定になる) |
| 1件も止められない妨害(死に札) | **0件** | 必須 |
| 攻撃1件あたりのカウンター種数(9種中) | 2〜4種 | 目標(🚧 v5未測定。v4実測は2〜3種) |
| 妨害1件あたりのカバー数(9件中) | 2〜4件 | 目標(🚧 v5未測定。v4実測は2〜3件) |
| 攻撃9種のコストの散らばり | 5種類以上 | 目標(🚧 v5未測定。v4実測は 6,8,11,13,14,15,16,17,19 の9種類) |
| 攻撃9種の発射行・向き(`antY`/`antDir`) | **すべて異なる** | 必須(識別を成立させるため。v5: 発射列 `antX` は可変になったため識別キーから外れた) |
| **攻撃**が `viable` | **必須** | `arrivalStep <= ATTACK_LIFE`(暫定値6,000)以内に敵陣へ到達できること。ETA の近似式ではなく直接シミュレーションで確認する。`ATTACK_LIFE` を確定させたら `isViableAtLife` で再シミュレーションなしに再判定できる |
| **攻撃**が `highway.fingerprintVerified` | **必須** | 最終選抜では厳密確認を通ったものだけを採る。`trajectoryPeriodic` のままにしない |
| **妨害**が有効な干渉を起こせる | **必須** | ⚠️ 妨害に「敵陣へ到達」を要求してはいけない。`DISRUPT_LIFE`(=1,000) では最大でも約56行しか進めず、192行先の敵陣には**設計上到達しない**(機能5の受け入れ条件そのもの)。妨害の射影条件は「`coverage > 0`(攻撃を1件以上止められる)」とする |
| **攻撃9種のハイウェイ署名(周期・並進)の種類数** | **3種類以上** | 目標(v4で追加) |
| 攻撃9種の実効色数(実際に踏まれた状態数)の種類数 | 2種類以上 | 目標(v4で追加) |

> ⚠️ **多様性を `rule.length` で測ってはいけない。** `LLRLLR` は `LLR` と力学的に同一(`rule[s % 3]` が同じ)なので、ルール長で数えると等価な弾を「別物」と誤認する。実測でこれが起き、宣言ルール長 3/6/9/14/15 の9種すべてがハイウェイ署名 period=18 / drift=(±1,±1) の**同一弾**だった。判定は必ず**ハイウェイ署名**か**実効色数**で行う。
| 各テンプレートの配置マス数 | **1個以上** | 必須。v3.1(120×60盤面)の実測では0マスの弾はコスト5(最安)で得点率43.8%になり、しかも軌道が発射位置だけで決まるので読み合いにならない。🚧 v5(256×256盤面)での0マス弾の得点率は未測定 |

> ⚠️ **到達時間は特徴軸として使えない(v3.1の実測)。** v3.1 の実測では得点できる攻撃の到達時間はすべて 13.3〜15.4秒 に収まった。ハイウェイの速度がほぼ一定なので当然で、差がつかない。
>
> MAP-Elites の特徴軸と UI の並べ替えは **コスト × 敵陣への進入位置(x座標帯)** を使うこと(進入位置はどの妨害が届くかを決めるので実質的な意味がある)。
> ⚠️ **v4 で軸が y → x に変わった。** 盤面を90度回転して攻撃軸が上下になったため、敵陣へ侵入するときに意味を持つ座標は x である(§14 の `entryPositionTier`)。`src/engine.js` の `simulateVersus` は `entryX` と `entryY` の両方を返すので、記述子には **`entryX`** を使う。v5 では `entryX` は得点ゲート判定にも使われる(`isInScoreGate`)。
>
> ただし v4 ではルールごとに速度が 0.0192〜0.0556 行/ステップ(約2.9倍)まで散るので、**到達時間は v3.1 と違って特徴軸になりうる**。選抜後に到達時間の散らばりを確認し、軸として使えるなら追加を検討する(下の「未決定事項」)。

## 8. 決定事項(意図的な割り切り)

すべて実測に基づく。詳細は [../REVIEW.md](../REVIEW.md) 付録C。

- ~~**RRL(3色)を採用し古典ラングトンのアリ(RL)を見送った**~~ **(v4 で解消)**: RL はハイウェイ形成に9,976ステップかかり、120×60・寿命2,400の設計では届かなかった。v4 で**ルールをテンプレートごとに持つようにしたため「1つを採用する」という決定自体が消えた**。RL(=`'RL'`, 2色)は選べるが、形成9,976ステップは寿命2,400の外なので実測の得点率は 0.00% で、選抜には残らない
- **寿命(最大ステップ数)で「ハイウェイ以外」を落とす**: 得点には88列の横断が必要で、カオス的運動は正味変位がほぼゼロなので原理的に届かない。実測でも、寿命の余裕を1.05倍から2.5倍まで変えても得点弾のHW割合は98%のまま変わらなかった(＝非ハイウェイは寿命を緩めても届かない)
- **得点条件は「敵の配置可能帯に入った瞬間」**: 「帯を突破して奥の端まで」にすると防御ブロックが効くようになるが(実測で64%減)、**妨害アリという別の防御手段を採用したため不要**と判断した
- **配置ブロックによる防御は機能しない**: 実測で、敵の配置可能帯に80個のブロックを置いても得点率は下がらなかった(アリは帯の1列目に触れた瞬間に得点するため)。防御はブロックではなく妨害アリで行う
- **盤面は完全には元に戻らない**: 複数アリが干渉するため。それが駆け引きの中心なので許容し、汚染度をバランス指標で監視する
- **テンプレートは妨害込みで評価し、攻撃と妨害を共進化させて生成する**: 空盤面だけで評価すると「妨害に強い配置」を選べない。実測では、攻撃側がカウンター数を最小化する探索をすると**わずか120回の評価(14秒)で、120種の妨害手札に一度も止められない攻撃が見つかる**。放置すると勝ち確定の弾ができてしまう。一方、防御側も3,000回程度の探索でその攻撃へのカウンターを必ず見つけられるので、交互に回せば健全な均衡に落ち着く(実測: 4ラウンドでカウンター密度が中央値3.6%→1.0%に下がり、カウンターを持たない攻撃は0件のまま安定)

### v4 で追加した決定事項

- **異種ルールの衝突は「余りとして解釈する」で吸収する**: 盤面は1枚を共有するのに色数がアリごとに違うため、ルールにない色を踏むことが必ず起こる。`board[i] % ant.colorCount` の1行で吸収し、この状態空間の圧縮そのものを干渉として扱う。分岐を増やさないので決定論性が保たれ、`engine.js` の1ステップ処理が単純なまま済む

- **ハイウェイの向きはルールでは変えられない(実測)**: 「ルールを変えれば横方向ハイウェイが作れる」という当初の想定は**実測で否定された**。ルール長2〜6の全114ルール × ランダム初期配置200通り(22,800試行)で検出した3,520件のハイウェイは、**並進ベクトルが例外なく (±1,±1) の45度**。4方向の違いは発射時の向きから来る。ルール選択が効くのは**速度(0.0192〜0.0556 列/ステップ)・形成ステップ(38〜25,952)・色数(干渉の非対称性)**である

- **探索の定義を「縦ハイウェイを探す」から改めた**: v4 の探索が解いている問題は、正確には次である。
  > **一般化ラングトンのアリの (ルール × 初期配置) 空間から、有限寿命・ラップ境界条件のもとで敵陣へ到達可能な周期移動体を探索する**

  「縦ハイウェイを主目的とする」という当初の研究仮説は、左右がラップする以上ゲーム上の必要条件ではない(45度でも巻きつきながら到達する)。上の定義がゲームと MAP-Elites 探索の双方に一致する。

- **⚠️ ゲーム候補の条件を正式に置き換えた**:

  | | 条件 |
  |---|---|
  | 旧 | `driftX === 0 && driftY > 0` |
  | **新** | **`GAME_PROJECTILE_LIFE` 以内に敵陣へ到達すること** |

  `direction` は**採否条件ではなく純粋な Behavior Descriptor** として扱う。第1アーカイブは `(direction, speed, formationTime, cost)` のままでよく、ゲーム投影の段階だけを `reachesEnemyZoneWithinLife === true` にする。

  ⚠️ 判定に **ETA の近似式を使わない。** 45度ハイウェイが左右にラップしながら進む場合、実効的な縦方向速度 `v_y = |Δy| / T` が十分なら弾として成立するので `ETA ≒ 残り縦距離 / |v_y|` は目安になるが、transient(形成前の非周期区間)とラップがあるため誤差が出る。**最終判定は必ず直接シミュレーションで敵陣到達を確認する**(`src/engine.js` の `simulateSolo` を実ゲーム条件で走らせる)。

  この緩和の根拠:
  - ルール長2〜16・セル状態自由の探索空間でも、`driftX === 0` のハイウェイは検出7,680件中**1件**(0.013%)しか出ない
  - しかもその1件(`RLRLRLLRRRLLRLLR`・16色・周期468・drift (0,-8)・形成1,192ステップ)は89行渡るのに約6,400ステップ必要で、**寿命2,400の2.7倍**。ゲームでは使えない
  - **左右がラップするので45度ハイウェイでも敵陣に到達できる。** 実ゲーム条件でランダム genome の1.81%が実際に得点する

  > 📌 **`driftX === 0` の希少性そのものは実験結果として保存する価値がある。** 「ルール長2〜16・セル状態自由の空間で、純粋な縦ハイウェイは7,680件中1件(0.013%)しか存在せず、その1件もゲーム寿命の2.7倍を要して到達不能」という測定は、**なぜゲーム採用条件を緩和したのかを説明する一次資料**である。`data/search-archive.json` には向きによらず全ハイウェイを保存し、この分布を後から再確認できるようにする(§23)。

- **探索評価とゲーム評価を別の盤面で走らせる**: §7 は「探索20,000ステップ / ゲーム採用2,400ステップ」と2つのレジームを分けているが、探索も実ゲーム盤面(60×120)で走らせると**アリが上下端で死ぬため20,000ステップに到達しない**(実測: 到達率 **11.6%**、軌跡長の中央値 1,889、20.3%が200ステップ未満)。短い軌跡に5周期の検出をかけると**過渡的な直進を大量に偽陽性としてハイウェイ判定してしまう**(§27 の false positive rejection がまさにこれ)。実害として、記述子の `direction` の **34%が `'N'`(純粋な縦)** になっていた — 独立実測では45度しか存在しないのに。
  したがって**探索評価だけ `C.SEARCH_BOARD_HEIGHT`(=4,096) の仮想盤面**(上下端なし・得点判定なし・左右ラップは実ゲームと同じ)で走らせる(`src/engine.js` の `simulateSearch`)。ゲーム評価は従来どおり `simulateSolo` を実ゲーム盤面で使う。
  修正後の実測: 20,000ステップ到達率 **100%**、`'N'` は **0.2%** まで低下し、並進ベクトルは対角 (±1,±1)/(±2,±2) が支配的になった。回帰フィクスチャ(`LEGACY_RULE` で `formationStep=38` / `period=18`)は不変。
  ⚠️ 代償として評価コストが約5.7倍(20,000 genome で 8.7秒 → 50秒、約400 genome/秒)になった。探索予算はこのスループットで見積もること。

- **⚠️ 攻撃アリの寿命を 2,400 → 3,600 に引き上げた(弾速の多様性を物理的に成立させるため)**:
  中間地帯88行を渡るのに必要なステップ数は速度クラスごとに `LLR`=1,621 / `RRRRL`=3,096 / `RRRLLL`=3,445 / `RRRRRL`=3,824 / `RL`=14,560 で、**寿命2,400 では `LLR` 系しか物理的に届かない**。
  実際、寿命2,400 で生成した攻撃9種は宣言ルール長が 3/6/9/14/15 とばらついていたのに、**実効色数は3か6、ハイウェイ署名は9種すべて period=18 / drift=(±1,±1) の1種類だけ**だった。`LLRLLR` は `rule[s % 3]` が `LLR` と同じなので**力学的に同一**で、長いルールの末尾は一度も踏まれない死にコードになる。つまり「ルールを選んで撃つ」という v4 の主目的が成立していなかった。
  3,600 にすると上位3クラス(`LLR` / `RRRRL` / `RRRLLL`)が届き、**到達時間に 13.5秒〜28.7秒 の差**が生まれて読み合いの軸になる。
  ⚠️ 代償として「寿命がハイウェイ以外を落とすフィルタ」という v3 からの設計原則が弱まる。`highwayShareOfScoring`(95%以上)を必ず再測定すること。

- **ルールは原始形(primitive root)に正規化する**: `LLRLLR` のように短いルールの繰り返しになっているルールは、`rule[s % 元の長さ]` が同じなので元のルールと**完全に同じ挙動**になる。多様性の判定を `rule.length` で行うと、こうした等価ルールを「別物」と数えてしまい、選抜が多様性を偽装できてしまう(実測でこれが起きた)。したがって:
  - genome のルールは**最小の繰り返し単位に還元**してから扱う
  - 9×9 選抜の多様性基準は `rule.length` ではなく**ハイウェイ署名(周期・並進・形成ステップ)**で測る。プレイヤーが実際に体験するのは弾速と到達時間であって、ルール文字列の長さではない

- **⚠️ `FIRE_TIMINGS` は `ATTACK_LIFE` から導出する(固定リストにしない)**: v3.1 の `[0, 150, ..., 1350]` は寿命2,400 用に決めた格子で、v4 で寿命を3,600 に上げたときに据え置いたため、**飛行後半をカバーする迎撃タイミングが存在しなくなった**。妨害は寿命400(≒3.3秒)なので1,350 に撃つとステップ1,750 には消えているが、低速クラスの弾の到達は 2,316〜3,458 ステップである。
  結果として「**低速の弾はどれ1つとしてカウンターを持てない**」状態になり、必須条件「カウンターを持たない攻撃=0件」によって低速弾が**構造的に選抜不可能**になっていた。目標「ハイウェイ署名3種類以上」が達成できなかった真因はこれ。
  実測(低速署名の viable 個体8件 vs 同じ妨害候補23件): 旧格子(最大1,350)でカウンターを持てたのは **0件/8件**、新格子(最大3,000)では **7件/8件**。成功した迎撃タイミングは**すべて1,650〜3,000**、つまり旧格子の完全に外側だった。
  → `FIRE_TIMINGS` は `0` から `ATTACK_LIFE - 600` まで150間隔で生成する。**寿命を変えたら格子も自動で追随する**ので、この失敗は再発しない。

- **ハイウェイ検出を正式に2段構えにした**:

  | | 検出方式 |
  |---|---|
  | 旧 | 全候補に正規化 fingerprint |
  | **新** | **軌跡の周期性による高速検出 → 採用候補のみ fingerprint 厳密検証** |

  MAP-Elites は評価回数が支配的なので、毎ステップの近傍ハッシュ化を全候補にかけるのは成立しない。パイプラインは次のとおり:

  ```text
  全 genome
     ↓ 位置 + 向きの周期検出（高速フィルタ）
  highway候補
     ↓ 5周期以上の連続一致
     ↓ ゲーム到達判定（寿命内に敵陣へ到達するか）
  有望候補のみ
     ↓ local fingerprint
  厳密 highway 確認
  ```

- **⚠️ `highway.detected` を単一の boolean にしない**: **軌跡の周期性はハイウェイの十分条件ではない**(位置と向きが周期的でも、周囲のセル状態が同じ構造を再生産しているとは限らない)。1つの boolean にまとめると、高速フィルタの近似が最終選抜まで素通りする。したがって2つに分ける。

  ```ts
  highway: {
    trajectoryPeriodic: boolean,   // 高速フィルタ(軌跡の周期性)を通った
    fingerprintVerified: boolean,  // 近傍状態の fingerprint による厳密確認を通った
    period: number,
    driftX: number,
    driftY: number,
    verifiedCycles: number,
    formationStep: number,
    speed: number,
  }
  ```

  使い分けを固定する。

  | 場面 | 使う値 |
  |---|---|
  | MAP-Elites 探索中(アーカイブ挿入・記述子計算) | **`trajectoryPeriodic`** |
  | 最終テンプレート選抜(9×9) | **`fingerprintVerified`** |

  探索中に厳密検証をかけるとスループットが破綻し、最終選抜で高速フィルタのまま通すと偽陽性が製品に混入する。この境界を跨がないこと。

- **PC・スマホ両対応を必須要件にした**: v3.1 でスコープ外にしていたモバイル対応を必須へ格上げした。v4 時点では盤面が 60×120 の縦長(1:2)で、広幅では盤面＋操作パネルの2カラム、狭幅では1カラムへリフローする方針だった。⚠️ v5 で盤面が 256×256(正方形・1:1)になったため、この縦長前提のレイアウト方針は再検討が必要(🚧 未着手。デザインの唯一の正は [../DESIGN.md](../DESIGN.md) と `src/tokens.css` だが、本ドキュメント更新の範囲では `DESIGN.md` は未確認・未更新)

- **セルの描画で「状態」と「陣営」を直交させた**: セルは状態0..15 と「最後に触れた陣営」の2情報を持つ。32色を用意するのではなく、**色相=陣営(藍=side1 / 朱=side2)・濃度=状態値**の2軸に分けた。`match.lastToucherSide` がこの色相側の入力になる。`lastToucher` によるクリーンアップ判定のロジックは変更していない

### v5 で追加した決定事項

- **盤面を 60×120 → 256×256(正方形)に拡大した**: より複雑なハイウェイと戦略が成立する余地を作るための設計判断。中間地帯が88行→192行になり横断距離が2.2倍になったため、寿命を3,600→6,000に、ステップ速度を120→300に引き上げて体感時間(11.6〜19.7秒)をv4と同水準に維持した。盤面セル数が7,200→65,536になったことで `engine.js` の全盤面走査(クリーンアップ)が支配的コストになったため、`ant.touched` によるインデックス走査に置き換えた(挙動は同値。`test/engine.test.js` に回帰テストあり)

- **得点ゲートを導入した**: 盤面を256列に広げ、かつ発射列を可変にしたことの帰結として、守る側は256列すべてを警戒しなければならず迎撃が成立しなくなる。得点を中央192列に限ることで「門を守る」という防衛目標を作り、`attacksWithoutCounter = 0`(必須条件)を満たせる幅に戻した。左右32列ずつは得点しない「壁」になる

- **発射列(antX)を可変にした**: 左右がトーラスである以上、x方向の平行移動は力学の厳密な対称性であり、同じテンプレートをどの列から撃っても軌道・周期・並進・形成ステップは変わらない。テンプレートを genome と同じ「アリからの相対座標」表現に揃えることで、Seed Distillation が生成する種(アリ周囲の局所セル)とも表現が一致する利点がある。帰結として `identifyTable` のキーが `"antX,antY,antDir"` → `"antY,antDir"` になり、`counterTable`/`escortTable` は絶対列ではなく `deltaX`(妨害の発射列−攻撃の発射列)の表になった

- **配置マスをアリ近傍(`TEMPLATE_CELL_RADIUS`=8)に限定した**: 盤面が256列になると配置帯は256×32=8,192マスになり、配置帯全体に一様に16マス撒くと密度0.2%になってアリが配置マスを一度も踏まない(=genomeの初期配置部分が無意味になる)ことが実測で分かった。アリの近傍に限定して撒くことで初期配置が軌道に効くようにした

- **`ATTACK_LIFE` を「探索をやり直さずに後から決められる」構造にした**: 探索中のゲーム射影は `ATTACK_LIFE` ではなく `GAME_LIFE_SEARCH_CAP`(=12,000)で走らせ、個体ごとの実到達ステップ数(`arrivalStep`)を記録する。探索後に `scripts/tune-attack-life.mjs` で `arrivalStep` の分布を掃引し、「viable件数/到達時間の分散/速度クラス被覆」から `ATTACK_LIFE` を決める。現在の6,000は**暫定値**(下の「未決定事項」参照)

- **Seed Distillation を導入した**: 通常の genome は「初期配置→transient→formationStep→highway」という流れを持ち、transient がそのままゲームでは「発射から弾が仕上がるまでの遅延」になる。発見済みハイウェイが形成された時点の局所盤面を切り出し、そのハイウェイ状態を直接開始できる有限初期配置(種)へ逆変換することで、「発見しやすいが形成が遅いハイウェイ」と「ゲームで即座に使えるハイウェイ種」を分離して探索する。蒸留 genome(`origin: 'distilled'`)は通常の個体と同様に MAP-Elites アーカイブへ再投入する(特別扱いしない)

- **ハイウェイ検出を `highway-trajectory.js`(高速フィルタ)と `highway-fingerprint.js`(厳密確認)の2モジュールに正式に分割した**: 探索評価と厳密検証は計算コストが大きく異なるため、ファイルを分けて責務を明確にした。`highway-detector.js` は既存の import 元を壊さないための再エクスポート専用ファサードとして残す

- **探索を `worker_threads` で並列化し、決定論を依存関係で担保した**: 乱数(genome生成・親選択・突然変異)をメインスレッドだけに置き、ワーカー(`scripts/lib/search-worker.mjs`)は「渡された genome を評価して返すだけの純粋関数」にした。結果は完了順ではなく**投入した添字順**にアーカイブへ挿入する。この2条件を守るかぎり、ワーカー数(`--workers`)を変えても `--seed` 固定で出力がバイト単位で一致する

- **`src/template.js` を独立モジュールとして切り出した**: `src/cpu.js` は `src/engine.js` を import してはいけない(実行時のシミュレーション探索をしないことを依存関係で担保するため)。一方、発射列が可変になったことで CPU もプレイヤーUIも「相対テンプレート→絶対座標」の変換が要る。これは純粋な座標計算でありシミュレーションではないため、`engine.js` から独立させて `engine`/`cpu`/`app`/`scripts` が同じ実装を共有できるようにした
