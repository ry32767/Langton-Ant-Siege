> **v3 の変更点**(v2 からの全面刷新)
> - 盤面を **120×60** に拡大。配置可能域を**自陣の外端の帯**に限定し、**敵の配置可能帯への到達**を得点条件にした
> - アリのルールを **RRL(3色)** に変更。古典ラングトンのアリ(RL)は本作の盤面・寿命ではハイウェイに到達できないことが実測で判明したため
> - **アリの寿命(最大ステップ数)**を導入。ハイウェイ級の直進運動でないと物理的に届かない設計にした
> - **複数アリの同時発射**と、安価な**妨害アリ**を導入。相手のハイウェイを壊しに行くのが防御手段になる
> - HP制から**得点制**に変更
>

> **v5 の変更点**(盤面拡大版)
> - **盤面を 60×120 → 256×256(正方形)に拡大**した。配置可能帯の深さ(`ZONE_DEPTH`)は16→32、中間地帯は88行→192行になった
> - **ステップ速度を 120 → 300 ステップ/秒**に上げ、盤面が縦長でなくなった分・横断距離が伸びた分の体感時間を旧版と同水準(11.6〜19.7秒)に維持した(⚠️ **v5.1 でさらに 670 に改定**。理由は下記「v5.1 の変更点」)
> - **得点ゲート**を導入した。敵陣(y≥`SCORE_LINE_Y`)に到達しても、そのときの x が盤面中央192列の外なら得点にならず消滅する(左右32列ずつが「壁」)
> - **発射列(`antX`)を可変**にした。テンプレートは発射列を持たず、配置マスは**アリからの相対座標** `[dx, dy, state]` で持つ。プレイヤー/CPU が発射時に列を選ぶ。左右がトーラスである以上、x方向の平行移動は力学の厳密な対称性であるため
> - 配置マスをアリの近傍(`TEMPLATE_CELL_RADIUS`=8)に限定した。配置帯全体に一様に撒くと密度が薄すぎてアリが配置マスを踏まなくなるため
> - **Seed Distillation** を導入した。発見したハイウェイの形成時点の局所盤面を切り出し、「そのハイウェイを即座に開始できる初期配置」へ逆変換し、MAP-Elites アーカイブへ再投入する(§10〜§24 相当。本書では機能として後述)
> - ハイウェイ検出を `src/search/highway-trajectory.js`(高速フィルタ)と `src/search/highway-fingerprint.js`(厳密確認)の2モジュールに正式に分割した(`highway-detector.js` は再エクスポートのファサード)
> - `ATTACK_LIFE` を**探索をやり直さずに後から決められる**構造にした。探索中のゲーム射影は `GAME_LIFE_SEARCH_CAP`(導入時は12,000固定。⚠️ **v5.1 で `ATTACK_LIFE` に連動する値へ変更**、現在は20,000)で走らせ、個体ごとの実到達ステップ数(`arrivalStep`)を記録し、`scripts/tune-attack-life.mjs` で寿命候補を掃引してから確定する
> - `src/engine.js` の `cleanupAnt` を、全盤面走査(65,536マス)から**アリごとの touched インデックス列**の走査に置き換えた(性能修正。挙動は同値)
> - 探索(`scripts/generate-templates.mjs`)を `worker_threads` で並列化した。乱数はメインスレッドだけが持ち、ワーカーは純粋関数。結果は完了順ではなく**投入した添字順**にアーカイブへ挿入するため、ワーカー数によらず `--seed` 固定で出力が一致する
> - `identifyTable` のキーが `"antX,antY,antDir"` → **`"antY,antDir"`** になった(発射列が可変になったため、攻撃9種は発射「行」と向きだけで識別できることが選抜の必須条件になった)
>
> **v5.1 の変更点**(`ATTACK_LIFE`/`STEPS_PER_SECOND` 確定版)
> - `ATTACK_LIFE` を暫定値6,000から**確定値20,000**にした。1,014万評価の探索アーカイブを `scripts/tune-attack-life.mjs` で掃引し、弾種の多様性が寿命に対して単調に増える(実測: 寿命6,000→viable 49件・ハイウェイ署名2種 / 9,000→128件・9種 / 12,000→356件・18種)一方、寿命を延ばしても得点弾のハイウェイ割合は乱数候補4,000件で常に100.0%(=非ハイウェイは寿命を緩めても届かない)ことを確認したうえで、テンポ(1発の滞空時間)を基準に20,000を選んだ
> - `STEPS_PER_SECOND` を 300 → **670** に引き上げた。到達時間の**比**(最遅弾/最速弾=5.8倍)はステップ速度に依存せず、変わるのは絶対時間だけ。670は最速弾の着弾を5.2秒確保できる下限として選んだ(900だと最速弾が3.9秒で着弾し、CPUの判断周期1秒に対し判断4回ぶんしか無く「識別→迎撃札を選ぶ→発射列を合わせる→撃つ」に足りない)
> - `TOTAL_STEPS` が 72,000 → **160,800**(=240秒 × 670ステップ/秒)になった
> - `GAME_LIFE_SEARCH_CAP` を固定値12,000から**`ATTACK_LIFE` に連動する値**に変更した(常に `ATTACK_LIFE` と同じ、現在20,000)。保存済み `arrivalStep` は保存当時のキャップまでしか記録されていないため、キャップより長い寿命へ再射影するときは `scripts/generate-templates.mjs --resume-archive` がアーカイブの genome を再評価する
> - `SEARCH_LIFE` を 20,000 → **30,000** に引き上げた
> - `FIRE_TIMINGS` の導出方法を「秒数比例の間隔」から**「本数14固定」**に変更した。比例のままだと `ATTACK_LIFE`=20,000 で候補が約50点に増え、カウンター表((攻撃×妨害×deltaX×タイミング)の直積)の計算量が3.8倍(約3時間)になるため
> - `ARCHIVE2.speedClassBins` を `[0.04, 0.048, 1.0]` → **`[0.025, 0.040, 1.0]`** に更新した(到達可能な v_y の範囲が 0.0097〜0.0556 に変わったことに伴う3等分点)
> - `DISRUPT_LIFE`(=1,000)は据え置いた。ただし `STEPS_PER_SECOND` の変更で実時間は3.3秒→**1.49秒**になった。この定数が担保しているのは実時間ではなく**到達距離**(空間的性質)なのでステップ速度に依存しない。ただし `ATTACK_LIFE` との比が 9:1 → 20:1 に広がったため、`counterDensityMedian`/`attacksWithoutCounter` への影響は🚧再測定が必要
>
> **v5.2 の変更点**(予約発射修正・自爆・CPU盤面観測・方策16次元化)
> - **予約発射のトークン確保(バグ修正)**: `cpu.js` の `decide()` が「予約したら null を返す」ため、同じ判断の中で tryAttack が予約分のトークンを使い切っていた。修正: 予約済み・未発火の発射コストを `commitments` に記録し、以降の判断で差し引く。実測(30試合×3方策): 握りつぶし率 **100% → 0.0%**、妨害発射数 **0.05 → 15.70 回/試合**。予約発射の採否も「現在のトークン」ではなく「発火時点の見込み残高」で判定するようにした
> - **自爆(`SELF_DESTRUCT_COST = 0`)**: プレイヤーは UI の「自爆」パネルから飛行中の自分のアリを消去。CPU は方策パラメータで判断。跡は通常の消滅と同じ `cleanupAnt` で消す(新経路を作らない)。結果、自爆は「自陣の汚染を自分で掃除する手」にもなる
> - **CPU が盤面を見られるように**: `createSideView` に `boardPollution` / `myZonePollution` / `enemyZonePollution`(いずれも 0..1)を追加。生配列ではなく派生スカラー。内部の増分カウンタ(`nonWhiteTotal`/`nonWhiteZone`)から O(1) で算出
> - **方策ベクトルが13 → 16次元**: `selfDestructBias`(基礎確率) / `selfDestructAgeFrac`(齢の下限) / `pollutionDestructWeight`(盤面汚染に比例する重み)を追加。判定は「飛行数上限の早期return より前」に行う(枠が埋まっているときこそ使いたいため)
> - **CEM の学習手順**: 共通乱数(CRN)で試合シード列を統一し、固定アンカー(無学習中立方策)を加えて fitness に組み込む
>
> **v5.5 の変更点**(3+3テンプレート化・低コスト妨害・役割別選抜)
> - **テンプレート数を9+9から3+3に削減**(差分仕様 §3)。攻撃は Speed/Economy/Robust、妨害は Cheap/General/Complement の3役割を1種ずつ選抜。目的は「UI上で各役割を理解しやすくする」「プレイヤーが手を読める手札数に削減する」「CPU方策空間を削減する」
> - **妨害の非対称コスト導入**(差分仕様 §10)。攻撃は従来通り `ATTACK_COST(5) + 配置マス数` だが、妨害は `DISRUPT_BASE_COST(2) + ceil(配置マス数/2)` に変更。迎撃札を実際に使える価格帯(3〜10)へ収める意図的な非対称ルール。`DISRUPT_BASE_COST` は従来の `DISRUPT_COST(3)` から改名・値を2に変更
> - **妨害テンプレート生成に Seed Compression を追加**(差分仕様 §7-8)。迎撃性能を維持しながら配置セル数を可能な限り削減。採用条件は「軌道条件を満たす」「空間制約を満たす」「迎撃能力を失わない」の3つ
> - **最終選抜が役割別に変更**(差分仕様 §13)。攻撃・妨害それぞれで役割ごとに候補を絞った後、3×3のセット評価も行う。「9×9の総合スコア上位9個」ではなく「役割×性能」で多次元比較する。攻撃A1/A2/A3がハイウェイ署名やコストで区別される必要がある(選抜の必須条件は別途更新)
> - **CEM方策が17次元から11次元に削減**。減った6次元は**すべて `attackPref[9]` → `attackPref[3]`** によるもので、他のパラメータの増減は無い(配列要素と攻撃3種の役割が `C.ATTACK_ROLES` の順で対応する)。⚠️ 探索予算(集団60・各40試合・エリート12・40世代)は**据え置く**。次元が減ったことを理由に予算まで同時に削ると、収束の改善が「次元削減の効果」なのか「予算変更の効果」なのか切り分けられなくなるため(差分仕様 §19)
>
> **v6 の変更点**(Action-Centric CPU・盤面観測・CEM学習基盤刷新)
> - **CPUの意思決定を「固定優先順位のヒューリスティック」から「候補生成 + 24次元線形評価器」の2段構成に全面刷新した**。唯一の実装契約は [action-centric-contract.md](action-centric-contract.md)(以下「契約書」)。本書はそれと矛盾しない範囲でゲームルール・受け入れ条件・検証戦略・決定事項を同期する。詳細な式・スキーマは重複させず契約書を参照する
> - **旧 `tryDefend() ?? tryEscort() ?? tryAttack()` という人間が決めた固定優先順位を廃止**。`generateActions(view, ctx)`(合法な Action を列挙するだけ・戦術判断はしない)→ `selectAction(view, actions, ctx)`(`score = Σ weights[i]*features[i]` の24次元線形評価器で最大スコアを選ぶ。同点は候補添字が小さい方)の2段構成にした
> - **Action 型は WAIT / FIRE / SELF_DESTRUCT の3種のみ**。ATTACK / DEFEND / ESCORT という Action 型は存在しない。`score(WAIT) = 0` 固定で、実行可能な Action がすべて0点未満なら WAIT が勝つ
> - **旧11次元の方策パラメータ**(`fireThreshold` / `reserveTokens` / `defendBias` / `escortBias` / `attackPref[3]` / `selfDestructBias` / `selfDestructRemainingTicks` / `pollutionDestructWeight` / `attackAvoidBias`)を**全廃**し、`data/policy.json` の `weights`(24要素の線形評価器の重み)ひとつに統合した
> - **飛行中の自軍アリは全部が SELF_DESTRUCT 候補**になった。年齢・残寿命・盤面汚染度による事前フィルタ(旧 `selfDestructRemainingTicks`)は廃止。年齢は特徴(#20 `destructAge`)として評価器に渡るだけで、候補生成の条件にはしない
> - **攻撃 FIRE を得点ゲート内だけに限定しない**。得点ゲート外(`scoreReachability=0`)の発射列も候補に残す。攻撃アリを妨害・護衛・囮・盤面操作として使う戦略を方策表現から排除しないため
> - **`counterTable` / `escortTable` / `identifyTable` を「候補生成情報」へ降格**した。「その表由来だから優先する」という選択規則は無い。`counterTable.successRate` は24特徴に含まれない(候補の列挙順を決めるためだけに使う)
> - **1判断=1アクション**にした。旧実装の「自爆してから攻撃」「攻撃と同時に護衛を予約」という抱き合わせは廃止
> - `src/engine.js` に **32×32 粗視化盤面**(`coarseNonWhite` / `coarseOwnedBySide`)と、**自軍飛行アリ最大4匹ぶんの ownership map**(`coarseOwnedByAnt` / `antSlotOccupant` / `lastToucherSlot`)を追加し、`createSideView` が参照渡しで公開するようにした。CPU は局所ではなく32×32全体を毎判断観測できる
> - `scripts/train-policy.mjs` を**24次元 対角ガウス CEM**に刷新した。fitness は **self-play 50% + 固定 Reference League 4種(`src/reference-policies.js` の `ATTACK_ONLY`/`CHEAP_SPAM`/`SAVE_AND_BURST`/`DEFEND_HEAVY`)50%**。5世代ごとの held-out validation と、20世代以降の plateau による early stop を導入し、最終世代の mean を無条件採用せず複数候補を固定シードで再評価して選ぶ
> - `scripts/evaluate-policy.mjs` を新設。`--mode bench`(学習前の性能計測。契約書 §9)と `--mode final`(リーグ4種×500試合+旧CPU 1,000試合の最終評価)
> - 旧CPU(v5.5)を `src/cpu-legacy.js` + `data/policy-v55.json` として凍結保存し、`evaluate-policy.mjs --mode final` が対戦相手として使う
> - `scripts/verify-v54.mjs` を退役させ `archive/verify-v54.mjs` へ移した。「迎撃/護衛/攻撃/自爆」という戦術カテゴリの集計は v6 の Action 型(WAIT/FIRE/SELF_DESTRUCT)と噛み合わないため。後継は `evaluate-policy.mjs --mode final` の戦術使用ログ(`tacticsLog`。fitness には使わない観測専用)
> - 学習・評価・バランス検証は実施済み。実測値は「v6 の学習後検証・バランス実測」節にまとめてある

## 1. 概要

- **一言コンセプト**: ラングトンのアリが敷く「ハイウェイ」を弾道として撃ち合う、1人用(vs CPU、CPU vs CPUモードあり)のリアルタイム攻城ゲーム
- **ターゲット**: 個人開発・GitHub Pagesでの公開

> 詳しい背景は ../README.md(重複させない)。

## 2. ゲームルール(全機能の前提)

実装前にここを読むこと。数値は `src/config.js` に一元化し、ハードコードしない。

### 盤面

```
        x=0                                                    256
   y=0  ┌───────────────────────────────────────────────────────┐
        │ side1 配置可能帯                                        │ y=0..31    ＝side2の得点目標
  y=32  ├───────────────────────────────────────────────────────┤
        │                                                       │
        │            中間地帯(配置不可)                           │ y=32..223(192行)  幅256・左右ラップ
        │                       │                               │
        │                       ▼ side1 のアリ                    │
 y=224  ├──────┬─────────────────────────────────┬──────────────┤
        │ 壁32列│      得点ゲート(中央192列)         │  壁32列       │ x<32 または x≥224 は得点ゲートの外
        │ side2 配置可能帯                                        │ y=224..255 ＝side1の得点目標
 y=255  └───────────────────────────────────────────────────────┘
        ゲート内(32<=x<224)に到達で1得点。ゲート外に到達した場合は得点せず消滅
```

| 項目 | 値 | 備考 |
|---|---|---|
| 盤面 | **256列 × 256行(正方形)** | **左右はラップ(トーラス)。上下の端に出たアリは消滅** |
| 配置可能帯の深さ | **32行**(`ZONE_DEPTH`) | side1 は y=0..31、side2 は y=224..255 |
| 中間地帯 | y=32..223(192行) | どちらも配置できない |
| **得点条件** | **敵の配置可能帯に到達**(side1 なら y≥224=`SCORE_LINE_Y`)、かつそのときの x が**得点ゲート**の内側(下記) | 到達で **1得点**。先に5得点で勝ち |
| **得点ゲート** | 盤面中央の192列(`SCORE_GATE_X_MIN`=32 以上 `SCORE_GATE_X_MAX`=224 未満) | ゲートの外(左右32列ずつの「壁」)に到達した場合は**得点せず消滅**する。詳細は[得点ゲート](#得点ゲートv5)を参照 |
| ステップ速度 | **670 ステップ/秒** | 論理は固定ステップ、描画は requestAnimationFrame。v4(120)→v5(300)→v5.1(670)。理由は下記「アリの種類と寿命」参照 |
| トークン | 毎秒 +1、上限 30 | アリ飛行中も蓄積する |
| 試合時間上限 | 240秒 | 時間切れ時は得点が多い方の勝ち。同点なら引き分け。`TOTAL_STEPS` = 240 × 670 = **160,800** |
| 同時飛行数 | 1陣営につき最大4匹 | 攻撃・妨害の区別なく合計4匹 |
| テンプレート数 | **攻撃3種・妨害3種**(v5.5) | 攻撃=Speed/Economy/Robust の3役割、妨害=Cheap/General/Complement の3役割を1種ずつ。**v5.5で変更**。人が把握して選べる手札数へ削減。候補プールから役割別に選抜する |
| 発射列 | **可変**(`antX`。発射時に選ぶ) | 詳細は[発射列の可変化](#発射列antXの可変化v5)を参照 |

### アリの移動規則(テンプレートごとの一般化ルール)

**グローバルなルールは存在しない。** 各テンプレート(＝そこから発射されるアリ)が自分のルールを持つ。

| 項目 | 規則 |
|---|---|
| `rule` | `'L'` / `'R'` だけからなる文字列。添字がセルの状態 |
| `colorCount` | `rule.length` と等しい。**2 ≤ colorCount ≤ 16** |
| ルールの変更 | 発射時にテンプレートから設定し、**そのアリが消滅するまで変更しない** |
| ルール長のコスト | **課さない**。コストは `baseCost + 配置セル数` のみ |

例: `rule = 'RLLRRLR'`(7色) なら、状態0で右・状態1で左・状態2で左・状態3で右…と回る。

1ステップの手順は次の順で行う。

1. **今乗っているマスの生値を読み、自分の色数で割った余りを状態とする**(下の[異種ルールの衝突](#異種ルールの衝突共通ルール))
2. **その状態**で回転を決める(`rule[状態]`)
3. マスの状態を1つ進める(`(状態 + 1) % colorCount`)
4. 向いている方向へ1マス前進する(**左右はラップ、上下はラップしない**)
5. 前進した結果で消滅・得点を判定する(下の[得点判定](#得点判定と盤面のクリーンアップ))

> ⚠️ **回転は「進める前の状態」で決める。** 進めた後の状態で判定すると別のセルオートマトンになり、ハイウェイの形成ステップも軌道もすべて変わる。参照実装(`src/engine.js` の `stepAnt`):
> ```js
> const raw = board[j];
> const s = raw % ant.colorCount;
> ant.dir = ant.rule[s] === 'R' ? (ant.dir + 1) & 3 : (ant.dir + 3) & 3;
> board[j] = (s + 1) % ant.colorCount;
> ```

### 異種ルールの衝突(共通ルール)

盤面は1枚を全アリで共有するが、色数はアリごとに違う。だから**ルールにない色を踏む**ことが起こる。
これを次の1行で吸収する。

```js
const s = board[i] % ant.colorCount;
```

例: 16色のアリが状態 `13` を残したセルに3色のアリが入ると、`13 % 3 = 1` として**状態1と解釈**し、その後 `1 → 2` へ書き換える。

> **この状態空間の圧縮そのものをゲーム上の干渉として扱う。** 色数の少ないアリは相手の高い状態値を踏み潰し、色数の多いアリは相手の軌跡を自分の広い状態空間で読む。ルール長の選択が干渉の非対称性として効いてくる。

### 得点ゲート(v5)

敵陣(side1 なら y≥`SCORE_LINE_Y`=224)に**到達しただけでは得点にならない**。到達した瞬間の x が盤面中央192列(`SCORE_GATE_X_MIN`=32 以上 `SCORE_GATE_X_MAX`=224 未満)の中に入っているときだけ1得点で、外に出た場合は**得点せず消滅**する。ゲートの外側(左右32列ずつ)は「壁」になる。

```js
// src/config.js の isInScoreGate()。engine の得点判定と UI の描画が共有する唯一の定義
export function isInScoreGate(x) {
  return x >= SCORE_GATE_X_MIN && x < SCORE_GATE_X_MAX;
}
```

⚠️ **盤面を256列に広げ、かつ発射列を可変にした**([発射列の可変化](#発射列antXの可変化v5)参照)ことの帰結として、守る側は256列すべてを警戒しなければならず迎撃が成立しなくなる。得点を中央192列に限ることで「門を守る」という防衛目標を作り、`attacksWithoutCounter = 0`(必須条件)を満たせる幅に戻す。

x はグローバル座標のまま両陣営で共通に判定できる(x は陣営間で鏡像にならない。鏡像になるのは y だけ)。

### 発射列(antX)の可変化(v5)

**テンプレートは発射列 `antX` を持たない。** 配置マス(`cells`)は**アリからの相対座標** `[dx, dy, state]` で持ち、プレイヤー/CPU が発射時に `antX`(0..255 の任意の列)を自由に選ぶ。

根拠: **左右がトーラスなので、x方向の平行移動は力学の厳密な対称性である。** 同じテンプレートをどの列から撃っても、軌道は平行移動するだけで形・周期・並進・形成ステップは変わらない。一方 `antY`(発射行)はテンプレート固有のまま変えられない — y方向の平行移動は得点ラインまでの距離を変え、寿命内に届くかどうかに影響するため。

帰結(v5):

- `identifyTable` のキーは `"antX,antY,antDir"` → **`"antY,antDir"`** になった。**攻撃3種が発射「行」と向きの組だけで識別できることが選抜の必須条件**(v5.5で変更。各役割1種ずつなら識別は依然一意)
- `counterTable[攻撃ID]` の各要素は `{ disruptId, deltaX, fireAtStep, successRate }`。`escortTable[攻撃ID][迎撃妨害ID]` の各要素は `{ interceptDeltaX, interceptFireAtStep, escortDisruptId, escortDeltaX, fireAtStep }`。`deltaX` は「妨害の発射列 − 攻撃の発射列」を `WIDTH` で割った余りで、絶対列ではなく**差分**の表になる
- 攻撃テンプレートは `entryXAt0`(発射列0で撃ったときに敵陣へ入る列)を持つ。実プレイでの到達列は `(antX + entryXAt0) mod WIDTH`。したがって「得点したいなら撃てる列は幅192列の連続区間(トーラス上)に限られる」という新しい駆け引きが生まれる(`src/template.js` の `scoringLaunchColumns` / `launchColumnScores` が計算する)
- 探索・カウンター表計算では `deltaX` を掃引するコストが生じる。共進化の途中は `COEVO_DELTA_X_STRIDE`(=16)の粗いグリッドで近似し、最終3×3のテーブル計算だけ全256列を掃引する(`scripts/generate-templates.mjs`。v5.5で変更)

### ハイウェイについて(実測)

ハイウェイの向きは**ルールでも初期配置でも変えられない**。ルール長2〜6の全114ルール × ランダム初期配置200通り(計22,800試行)で検出された3,520件のハイウェイは、**すべて並進ベクトルが (±1, ±1) の45度**だった。4方向の違いは**発射時の向き**から来る。

ルール長を2〜16へ、配置セルの状態を自由にまで広げると45度以外も現れるが、極めて希少(検出7,680件中13件・0.17%)。

したがって**ルール選択が効くのは向きではなく速度・形成ステップ・色数**である。

| ルール | 色数 | 周期 | 行/ステップ | 形成ステップ |
|---|---|---|---|---|
| `RRL` / `LLR` | 3 | 18 | **0.0556** | 38 |
| `RRRRL` / `LLLLR` | 5 | 68 | 0.0294 | 102 |
| `RRRLLL` / `LLLRRR` | 6 | 38 | 0.0263 | 98 |
| `RRRRRL` / `LLLLLR` | 6 | 84 | 0.0238 | 126 |
| `RL` / `LR`(古典) | 2 | 104 | 0.0192 | **9,976**(寿命外) |

> 上表の周期・速度・形成ステップは**セルオートマトンのルールだけで決まる CA 固有の値**で盤面サイズに依存しないため、v4 実測のまま有効(単位を「列」から「行」に修正しただけ)。一方、下の「左右がラップするので〜」の得点率・到達ステップは**盤面サイズと寿命に依存する v3.1(120×60・寿命2,400)実測**であり、v5.1(256×256・寿命20,000)では未再測定。
>
> 🚧 **未測定(本探索後に埋める)**: v5 盤面(256×256)でのランダム genome の得点率・到達ステップ分布。

`C.LEGACY_RULE`(=`'RRL'`)は**回帰フィクスチャ専用**の定数で、既定ルールではない。

### 自爆

| 項目 | 規則 |
|---|---|
| コスト | **0**(無料・払い戻しなし)。`SELF_DESTRUCT_COST` |
| 対象 | **自分の陣営の飛行中のアリだけ**(敵のアリIDを渡すと失敗) |
| 跡の処理 | 配置マス・踏んだマスは**通常の消滅と同じ `cleanupAnt` で消す**(新しい経路を作らない)。結果、自爆は「自陣の汚染を自分で掃除する手」にもなる |
| 得点 | **しない**。`score` / `scoredAnts` は増えない |
| プレイヤー操作 | UI の「自爆」パネルから飛行中の自分のアリを選んで消す |
| CPU による採否判定(v6) | **飛行中の自軍アリは全部が SELF_DESTRUCT 候補**になる。年齢・残寿命・盤面汚染度による事前フィルタは無い(旧 `selfDestructRemainingTicks` は廃止)。候補それぞれに `SELF_DESTRUCT` の Action として24次元の特徴(寿命消化割合=特徴20 `destructAge`、所有軌跡=特徴21〜23)を計算し、`generateActions`/`selectAction` の共通ロジックで他の FIRE / WAIT 候補と一緒にスコア比較する。年齢・所有量が大きいほど選ばれやすい**傾向を持つかどうかは学習結果次第**であり、規則としては強制しない。詳細は[CPUの盤面観測](#cpuの盤面観測v6)と契約書 §2/§5/§6を参照 |

### 配置マスの書き込み(発射時の盤面操作)

検証スクリプト(`verify-v3/*.mjs` の `place()` / `matchbench.mjs`)で確定している挙動。実装はこれに合わせる。

| 項目 | 規則 |
|---|---|
| 書き込む状態 | **テンプレートが指定した状態**(`cells` の3要素目)。固定値ではない。制約は `0 ≤ state < rule.length` |
| 既に非白のマスと重なった場合 | **無条件で上書き**する(加算しない・配置不可にもしない) |
| 配置マスの下限 | **規則上は0個**(アリだけの発射も成立する)。ただし**テンプレート/genome は1個以上を必須**とする(下記) |
| アリの初期位置 | 自陣の配置可能帯の中(side1 なら x は発射時に自由に選べる0..255の任意の列、y=0..31)。**配置マスと重なってよい** |
| 配置マスの座標 | **v5: アリからの相対座標**(`[dx, dy, state]`)で持つ。アリの近傍(チェビシェフ半径 `TEMPLATE_CELL_RADIUS`=8)に限定される。配置帯全体(256×32=8,192マス)に一様に撒くと密度0.2%になりアリが配置マスを一度も踏まないため(v4 実測で判明) |

| 0マス発射の危険性 | アリ1匹だけでも敷いたハイウェイで得点できてしまい、しかも軌道が発射位置と向きだけで決まるので読み合いにならない。コスト最安の手なので、テンプレートに0マスのものを混ぜてはならない |
| 発射時の `lastToucher` | 置いた配置マスの `lastToucher` を**そのアリのIDで埋める**(-1 のままにしない)。他のアリが後から踏むとIDが上書きされ、そのマスはクリーンアップ対象から外れる |
| 発射したステップの扱い | 配置マスを書き込んだ**同じステップ内でそのアリも1歩進む**(次のステップまで待たない) |

### 得点判定と盤面のクリーンアップ

判定はすべて**前進した後**に、次の順で行う。

1. 前進先が自陣側の端の外(side1 なら y<0)なら消滅(得点なし)
2. 前進先が敵の配置可能帯(side1 なら y≥224=`SCORE_LINE_Y`)なら、そのときの x が[得点ゲート](#得点ゲートv5)の中かどうかを判定する。中なら陣営に **1得点**してアリは消滅、外なら得点せず消滅する
3. 上のどちらでもなく `steps >= life` になったら消滅(得点なし)

> 得点したマスの状態は書き換わらない(状態更新は前進**前**のマスに対して行うため)。したがって敵陣の帯は攻撃アリによって汚れない。
> 下端(y≥256)の場外判定は書かなくてよい。y≥224 で先に得点判定が入るため到達しない。
> **左右に場外は無い**(x はトーラス)。
> ⚠️ **`cleanupAnt` の性能修正(v5)**: 盤面が 7,200 → 65,536 マスになったため、消滅時の「`lastToucher` が自分と一致する全マス」を全盤面走査で探すと1試合あたり数十匹の消滅がボトルネックになる。`src/engine.js` は代わりに、アリが移動のたびに踏んだマスの添字を `ant.touched` に記録しておき、消滅時はそこだけを見る(結果は全盤面走査と同値。`test/engine.test.js` に回帰テストあり)。

アリ消滅時、次の2種類のマスを白(状態0)に戻す。

- その発射で置いた配置マスのうち、**他のアリが触れていないもの**
- そのアリが最後に触れたマス(`Cell.lastToucher` がそのアリと一致するマス)

> ⚠️ 複数のアリが同じマスを踏み合うため、**盤面は完全には元に戻らない**。これは意図した仕様で、干渉こそが本作の駆け引きの中心。ただし汚れが蓄積しすぎるとテンプレートの予測値が信用できなくなるため、`simulate-matches.mjs` で試合終盤の盤面汚染度を必ず計測する(下の[検証戦略](#6-検証戦略)参照)。

### 護衛(escort)

妨害アリは**自分の攻撃を守るためにも使える**。相手の迎撃アリが自分の攻撃の軌跡を壊しに来る前に、その経路へ自分の妨害アリを送り込めば、迎撃側の軌道が崩れて攻撃が生き残る。

新しい機能ではなく、**「妨害アリはどのアリの軌跡にも干渉する」という既存ルールの帰結**。ただしゲームの深さの中心なので明記し、CPU にも実装する。

実測(下の[検証戦略](#6-検証戦略)のバランス指標に反映):

| 状況 | 攻撃の突破率 |
|---|---|
| 攻撃のみ vs 有効な迎撃 | **0%**(必ず止まる) |
| 攻撃＋護衛 vs 同じ迎撃 | **100%**(護衛を200回探索した場合) |
| 護衛付き攻撃 vs 新たに探した迎撃 | 6件中6件で有効な迎撃が見つかる |

> ⚠️ この実測は `verify-v3/escort.mjs` が**発射順**にアリを動かして測った値で、本仕様のステップ順序(下の[共有盤面とステップ順序](#共有盤面とステップ順序)。陣営単位で、しかも手番が毎ステップ入れ替わる)とは食い違う。`src/engine.js` で再測定したとき 0%/100% がそのまま出なくても回帰ではない。合格ラインは下の[バランス指標](#バランス指標simulate-matchesmjs-の合格ライン)の「攻撃＋護衛 vs 同じ迎撃の突破率 60〜100%」で判定する。

**攻撃 → 迎撃 → 護衛 → 再迎撃** と重ねるほどトークンを消費するので、どこで降りるかの読み合いになる。

> ⚠️ **v6 での位置づけ**: `escortTable` は「先回りで護衛の候補を生成する情報」に降格した(契約書 §3-5)。CPU に「護衛」という戦術カテゴリは存在しない。護衛由来の FIRE 候補も、通常の攻撃・妨害候補と同じ24次元評価器で他候補と比較され、スコアが勝てば選ばれるだけである。**護衛の候補を生成しても、学習の結果として一度も選ばれない(=使わない)ことは正当な結果として許容する**(旧 `escortBias` のような「使用確率」パラメータは存在しない)。旧実装固有だった「自分の攻撃を撃ったその場で予測予約する」という抱き合わせ処理も、v6 は1判断=1アクションの原則により廃止した(護衛候補が選ばれるのは、それ単独が最高スコアの判断として選ばれたときだけ)。

### 共有盤面とステップ順序

盤面は1枚を両陣営で共有する。1ステップの処理順は次で固定する。順序を固定しないと結果が再現しない。

1. **トークン加算**(`TOKEN_TICK_STEPS`=670ステップに1回。ステップ0でも加算するので、試合開始直後の保有は1)
2. **予約発射の反映**(`counterTable` / `escortTable` で記録した発射を `fireAtStep` ちょうどに実行する。配置マスの書き込みもここ)
3. **新しい判断**(`DECISION_INTERVAL_STEPS`=670ステップに1回)
4. **アリの移動**(先手の陣営 → 後手の陣営の順で、それぞれ発射順に全部移動)
5. **勝敗判定**(どちらかが5得点していたら終了)

#### 両陣営の判断は「同時」に行う

判断フェーズ(3)では、**先に両陣営の view を取得してから**、それぞれの `decide` を呼ぶ。逐次に処理すると、後に判断する側だけが「相手がこのステップで撃ったばかりのアリ」を view で見られてしまい、情報の非対称が生まれる。

実測: 逐次判断だと **先手勝率100%・平均得点 4.88 対 2.04**（攻撃の得点率が side1=28.7% 対 side2=14.8%）という露骨な偏りが出た。同時判断に変えたことで **先手勝率 50.4%**（3,000試合）に是正された。

#### 発射と移動の手番は1ステップごとに入れ替える

ステップ `s` での予約発射(2)と移動(4)の処理順は、**偶数ステップは side1 が先、奇数ステップは side2 が先**とする(`src/config.js` の `ALTERNATE_STEP_ORDER`)。同じ陣営が毎ステップ先に盤面へ書き込むのを避けるため。

> ⚠️ **注意**: 判断フェーズ(3)の手番を「ステップ番号 `s` の偶奇」で入れ替えてはいけない。判断は670ステップに1回しか走らず、670は偶数なので、ステップ番号の偶奇では**永久に同じ陣営が先**になる。判断フェーズは「判断が何回目か」(`floor(s / 670) % 2`)の偶奇で入れ替える。

**CPU の意思決定は670ステップに1回**(トークン加算と同じ周期。`DECISION_INTERVAL_STEPS`=`STEPS_PER_SECOND`)に固定する。実行時探索をしないので毎ステップ考える必要がなく、周期を固定しておくと自己対戦の結果が再現する。**プレイヤーの発射は押した次のステップで反映**する(待たせない)。

> ⚠️ **予約した発射は670の周期に縛られない。** `FIRE_TIMINGS` は `ATTACK_LIFE` から導出する(固定リストではない。`src/config.js` の `FIRE_TIMING_INTERVAL`/`FIRE_TIMING_LAST` 参照)。**v5.1 で導出方法を「秒数比例の間隔」から「本数14固定」に変更した**(理由は下記)。`ATTACK_LIFE`=20,000(確定値)では終端 `FIRE_TIMING_LAST` = `ATTACK_LIFE` − `DISRUPT_LIFE`×1.5 = 18,500 を「本数14(=間隔の数13)」で割って50刻みに丸めた**間隔1,400**になり、`[0, 1400, 2800, ..., 18200]` の**14通り**になる。うち `DECISION_INTERVAL_STEPS`(=670)の倍数は **0のみ**。「意思決定は670ステップ周期」だけを規則にすると、記録された `fireAtStep: 1400` のような迎撃が**物理的に撃てなくなる**。したがって:
>
> - **新しい判断**(何を撃つか決める)は670ステップに1回
> - **その判断で予約した発射**(迎撃・護衛)は、記録された `fireAtStep` の**そのステップちょうど**に実行する
>
> 予約は決定論的なので再現性は保たれる。これを変える(例: `FIRE_TIMINGS` を670の倍数に丸める)場合、REVIEW.md 付録D/E のカウンター数・突破率は別のタイミング格子で測った値になるので、**テンプレートの再生成と再計測が必要**。
>
> ⚠️ **`FIRE_TIMINGS` を「秒数比例の間隔」で導出してはいけない(v5.1の教訓)**: 比例のままだと `ATTACK_LIFE`=20,000 で候補が約50点に増え、カウンター表((攻撃×妨害×deltaX×タイミング)の直積)の計算量が3.8倍(約3時間)になり、最終選抜が探索本体より長くなる。そこで**候補の「本数」を寿命によらず一定(`FIRE_TIMING_COUNT`=14)に保ち、間隔(`FIRE_TIMING_INTERVAL`)の方を寿命に比例させる**方式に変えた。`ATTACK_LIFE` を実測で確定させても件数14は変わらず、間隔と終端だけが自動で追随する。間隔が `DECISION_INTERVAL_STEPS` の倍数になった場合は50ずらして避ける(`src/config.js` 参照)。

> `verify-v3/matchbench.mjs` の `match()` がこの順序の参照実装。

### 陣営の座標系(ミラーリング)

**side1(上)** のローカル座標がグローバル座標。**side2(下)** は上下反転。

| 対象 | 変換 |
|---|---|
| x座標 | **変換しない**(`xGlobal = xLocal`) |
| y座標 | `yGlobal = 255 - yLocal`(= `HEIGHT - 1 - yLocal`) |
| 向き | `up ⇄ down` を入れ替える(`left` / `right` はそのまま) |

`data/templates.json` の座標・向きは**すべて side1 ローカル座標で保存**し、side2 が使うときに変換する。

### 乱数とシード

乱数は「CPUがテンプレート候補から1つ選ぶ」ところだけで使う。試合開始時にシードを決めて `Match.seed` に保持し、決定論的な擬似乱数(xorshift等)で進める。`scripts/simulate-matches.mjs` は `--seed <n>` でシードを固定でき、同じシードなら結果が完全に再現する。

### CPUの盤面観測(v6)

CPU(機能6)は256×256の実盤面を毎判断走査すると学習が終わらないため、8×8セルを1ブロックに畳んだ **32×32の粗視化盤面**を `src/engine.js` が**増分更新**で持ち、CPU は局所ではなく32×32全体を毎判断観測する。**唯一の実装契約は [action-centric-contract.md](action-centric-contract.md)**(以下「契約書」)。ここでは `src/config.js` の値だけを一覧する。式・スキーマは重複させないので契約書を参照する。

| 定数 | 値 | 意味 |
|---|---|---|
| `COARSE_SIZE` | 32 | 粗視化盤面の一辺(32×32) |
| `COARSE_BLOCK` | 8(`=WIDTH/COARSE_SIZE`) | 1ブロックが何セル四方か |
| `COARSE_SHIFT` | 3(`=log2(COARSE_BLOCK)`) | `x >> COARSE_SHIFT` で coarse 列を求める |
| `COARSE_BAND_COUNT` | 4 | 盤面をCPUローカルYで4分割した帯の数(band0=自陣側、band3=敵陣側) |
| `COARSE_ROWS_PER_BAND` | 8(`=COARSE_SIZE/COARSE_BAND_COUNT`) | 1帯あたりのcoarse行数 |
| `OWNED_SPREAD_SCALE` | ≈90.5(`=hypot(WIDTH/4, HEIGHT/4)`) | 特徴23 `ownedTrailSpread` の正規化スケール |
| `ACTION_ATTACK_GATE_SAMPLES` | 4 | 攻撃発射列を得点ゲート内からサンプルする本数 |
| `ACTION_ATTACK_OFFGATE_SAMPLES` | 2 | 攻撃発射列を得点ゲート**外**からサンプルする本数(0にしてはいけない。契約書 §3) |
| `ACTION_DISRUPT_SAMPLES` | 4 | 妨害発射列を全256列からサンプルする本数 |
| `ACTION_COUNTER_MAX` | 8 | `counterTable` 由来の候補上限(全敵アリ合計) |
| `ACTION_ESCORT_MAX` | 4 | `escortTable` 由来の候補上限(全自軍攻撃アリ合計) |
| `ACTION_FEATURE_COUNT` | 24 | Action 評価器(線形)の次元数。`data/policy.json` の `weights` の長さと一致 |
| `FEATURE_SCHEMA_VERSION` | 1 | 24特徴の定義バージョン。定義を変えたら必ず上げる |
| `BURST_THRESHOLD` | 20 | Reference League `SAVE_AND_BURST` が撃ち始めるトークン閾値。CEM の学習対象ではない |

24次元 Feature Encoder(`encodeFeatures(view, action, ctx)`)の各特徴の定義・範囲は**契約書 §5 が唯一の定義**(本書では二重管理しない)。

## 3. 機能一覧

### ✅ MVP

#### 機能1：アリ・シミュレーションエンジン(RRL)
- [ ] 状態0または1のマスにいる時、状態を1つ進め、右に90度回転してから1マス前進する
- [ ] 状態2のマスにいる時、状態を0に戻し、左に90度回転してから1マス前進する
- [ ] 盤面の**左右**端を越えた移動は反対側の端に回り込む(トーラス。x=-1→x=255、x=256→x=0)
- [ ] **上**の端(y<0)を越えたアリは消滅し、得点は発生しない(下端は y≥224 で先に得点判定が入るため到達しない)
- [ ] 任意のルール(`RL` / `RRL` / 16色ルール)を指定でき、それぞれ指定どおりに回転する
- [ ] ルールにない色を踏んだとき、`board[i] % colorCount` として解釈される(状態13のマスに3色アリを置くと状態1として動く)
- [ ] 異なる色数のアリを同じ盤面で同時に走らせられる
- [ ] 寿命(攻撃20,000 / 妨害6,000ステップ。v5.3で妨害が1,000→6,000に変更)を使い切ったアリは消滅し、得点は発生しない
- [ ] 空盤面でアリを走らせると **38ステップ目からハイウェイ状態**(周期18で毎回同じ斜め1マスの並進)になる(`LEGACY_RULE` の回帰フィクスチャ。盤面サイズに依存しない CA 固有の値)
- [ ] 敵陣(y≥224)に到達しても、そのときの x が得点ゲート(32≤x<224)の外なら得点にならず消滅する

#### 機能2：準備フェーズ(資源トークン)
- [ ] 試合開始と同時に両陣営のトークンが0からスタートし、1秒ごとに+1される
- [ ] トークンは上限30で頭打ちになり、それ以上は蓄積されない
- [ ] アリ飛行中もトークンは蓄積される
- [ ] 配置マスは自陣の配置可能帯(side1 なら y=0..31)にのみ置け、y=32 以降には置けない
- [ ] 配置マスは指定された状態(`[dx, dy, state]` の3要素目)で書き込まれる
- [ ] 配置マスは1回の発射につき最大16個まで
- [ ] 発射コストは「攻撃アリ 5 + 配置マス数 / 妨害アリ 2 + ceil(配置マス数/2)」。**v5.5で妨害の非対称コスト導入**(§10)
- [ ] 保有トークンがコスト未満のとき、発射ボタンが無効化されて押せない
- [ ] 自陣のアリが4匹飛行中のとき、発射ボタンが無効化されて押せない
- [ ] 発射時、コスト分のトークンが消費される
- [ ] プレイヤー/CPU は発射時に発射列(`antX`。0..255)を自由に選べる

#### 機能3：テンプレート選択(3種 + 3種)
- [ ] 攻撃3種・妨害3種のテンプレートが**役割別に**タブで分かれて一覧表示される。攻撃=Speed/Economy/Robust、妨害=Cheap/General/Complement(v5.5)
- [ ] 攻撃テンプレートには **コスト・到達時間(秒)・カウンター数**(3種の妨害のうち何種で止められるか)が表示される
- [ ] 妨害テンプレートには **コスト・到達距離(行)・カバー数**(3種の攻撃のうち何種を止められるか)が表示される
- [ ] 保有トークンがコスト未満のテンプレートはグレーアウトされ、クリックしても選択されない
- [ ] テンプレートを選ぶと、選んだ発射列(`antX`)に応じて配置マスとアリの位置・向きが盤面上にプレビュー表示される
- [ ] 飛行中の敵の攻撃アリには**どのテンプレートか(A1〜A3)と役割が表示される**(発射行(`antY`)と向きで一意に識別できる。**v5.5で3種に削減**。`identifyTable` のキーは `"antY,antDir"`)
- [ ] 敵の攻撃を選択すると、それを止められる妨害テンプレートと推奨発射列(`deltaX`)・推奨発射タイミングが強調表示される

> **自由入力(テンプレート以外の配置)は MVP では実装しない。** 理由は3つ。①3種に絞った(v5.5)からこそ「相手が何を撃ったか」を役割と共に識別して読み合いができる。自由入力を許すと識別が成立しない。②実測では良い配置は乱数探索で上位0.1%以下なので、プレイヤーが自力で有効な弾を作るのは事実上不可能で、トークンを捨てるだけになる。③UIが複雑になる。Phase 2 で「識別されない代わりに性能も読めない上級者向けの弾」として検討する。

#### 機能4：発射と得点判定
- [ ] 発射ボタン押下で、下書きの配置マスとアリが自陣の配置可能帯に設置され、そのアリのシミュレーションが開始する
- [ ] アリが敵の配置可能帯(side1 なら y≥224)に入り、かつそのときの x が得点ゲート(32≤x<224)の中である瞬間、その陣営に1得点が入りアリが消滅する
- [ ] アリが敵の配置可能帯に入ったが x が得点ゲートの外(壁)だった場合、得点は発生せずアリが消滅する
- [ ] アリが自陣側の端を越えた場合(side1 なら y<0)、得点は発生せずアリが消滅する(敵側の端に出る前に得点判定が入るため、そちらは発生しない)
- [ ] アリが寿命を使い切った場合、得点は発生せずアリが消滅する
- [ ] アリ消滅時、「その発射で置いた配置マスのうち他のアリが触れていないもの」と「`lastToucher` がそのアリと一致するマス」を状態0に戻す
- [ ] 他のアリが踏んだマスは、そのアリの消滅時に消えずに残る

#### 機能5：妨害
- [ ] 妨害アリは攻撃アリと同じルールで動き、寿命だけが短い(6,000ステップ)
- [ ] 妨害アリも攻撃アリと同じ得点判定ロジックを通る(種類による特別扱いのコードを書かない)。ただし自陣ローカル座標の `y >= DISRUPT_MAX_LOCAL_Y`(=128=盤面中央)に到達した瞬間に消滅するため、敵陣(y≥224)には**到達しない**(空間的な制約であり、テンプレート再生成に依らず常に成立)
- [ ] 飛行中の敵のアリの軌跡を妨害アリが踏むと、そのマスの状態が変わり、敵のアリのその後の軌道が変化する
- [ ] 妨害アリ自身も相手の軌跡の影響を受ける(特別扱いはしない)

#### 機能6：CPU AI(Action-Centric。v6で全面刷新)

> **唯一の実装契約は [action-centric-contract.md](action-centric-contract.md)**(以下「契約書」)。engine / cpu / 学習 / 評価 / テストの各実装はこの文書だけを見て書ける。本節はゲームルール文書として矛盾しない範囲で要約し、式・スキーマは契約書へのリンクで済ませる(二重管理しない)。

CPUは**「戦術(どの札がどの札に勝つか)を事前計算テーブルで持ち、戦略(いつ何にトークンを使うか)を自己対戦で学習する」という大枠は維持しつつ**、v5.5までの「固定優先順位のヒューリスティック + カテゴリ別パラメータ」から、**「合法な Action を列挙する `generateActions` → 24次元の線形評価器で選ぶ `selectAction` 」の2段構成**へ全面刷新した(差分仕様 §1〜§20)。実行時の探索はしない(この制約は不変)。

**Action の形**(契約書 §2)。**WAIT / FIRE / SELF_DESTRUCT の3種類のみ**存在する。ATTACK / DEFEND / ESCORT という Action 型は無い(「迎撃」「護衛」は妨害 FIRE の由来を示すログ用ラベルにすぎず、選択規則には使わない)。

| Action | 内容 |
|---|---|
| `WAIT` | 何もしない。**`score(WAIT) = 0` 固定**。他のすべての Action が0点未満ならこれが選ばれる |
| `FIRE` | 即時(`atStep === view.step`)または予約(`atStep > view.step`)の発射。`kind: 'attack'\|'disrupt'` はテンプレートの物理的種別であって戦術ラベルではない |
| `SELF_DESTRUCT` | 飛行中の自軍アリ1匹を消す。**飛行中の自軍アリは全部が候補**(年齢・残寿命・盤面汚染度による事前フィルタは無い) |

**事前計算テーブル**(`data/templates.json` に同梱。v6では「候補生成情報」に位置づけが変わった。契約書 §3-4/§3-5/§9)

| テーブル | 内容 | v6での位置づけ |
|---|---|---|
| `counterTable[攻撃ID]` | その攻撃を止められる `{disruptId, deltaX, fireAtStep, successRate}` の一覧。`deltaX` は「妨害の発射列−攻撃の発射列」の余り | `generateActions` が迎撃由来のFIRE候補を作るための材料。`successRate` は候補の列挙順(降順)にのみ使い、**24特徴には含めない** |
| `escortTable[攻撃ID][迎撃妨害ID]` | その迎撃を無効化できる `{interceptDeltaX, interceptFireAtStep, escortDisruptId, escortDeltaX, fireAtStep}` の一覧 | `generateActions` が護衛由来のFIRE候補を作るための材料(先回りの予測。敵の迎撃を実際に観測する必要はない) |
| `identifyTable` | 発射行(`antY`)・向き → 攻撃ID(キーは `"antY,antDir"`。3種は `antY`・向き・役割の組がすべて異なるので1ステップで一意に決まる) | 迎撃候補の起点(`enemyAnt.spawnY,spawnDir` から攻撃IDを特定する)としてのみ使う |

**受け入れ条件**

- [ ] `data/templates.json` と `data/policy.json` を試合開始前に読み込む。`src/app.js` は `weights: policyData.weights` を CPU へ渡す(旧 `policy` オブジェクトは存在しない)
- [ ] `src/cpu.js` は `src/engine.js` のシミュレーション関数を一切呼ばない(実行時探索をしないことをコード上の依存関係で担保する)。テンプレートの座標変換(相対→絶対)は `src/template.js` を使う(`engine.js` を経由しない)
- [ ] `generateActions(view, ctx)` に**固定の戦術優先順位が存在しない**(「敵が来たら迎撃を優先する」等の分岐を持たない。候補を列挙するだけ)
- [ ] `selectAction` は `score = Σ weights[i]*features[i]` の**24次元線形評価器**で最大スコアの Action を選ぶ。同点は候補配列の添字が小さい方
- [ ] **24特徴すべてが死に次元ではない**(各特徴について、その次元の重みだけを大きく振ると選ばれる Action の順位が変わる。契約書 §5の凍結表と一致)
- [ ] **飛行中の自軍アリは全部が SELF_DESTRUCT 候補になる**(年齢・残寿命・盤面汚染度による事前フィルタをしない)
- [ ] CPU は 32×32 の粗視化盤面(`coarseNonWhite`)と自軍アリ別 ownership map(`coarseAntOwned`)を通じて**盤面全体を毎判断観測できる**(局所ではない)
- [ ] `coarseOwnedByAnt` から求めた `ownedTrailAmount` が、そのアリの消滅時に実際にクリーンアップされるセル数と一致する
- [ ] 敵の攻撃アリが出現したら、その発射行(`antY`)・向きから `identifyTable` を引いて攻撃IDを特定し、`counterTable` 由来の迎撃 FIRE を候補化できる
- [ ] 迎撃候補の発射列は `wrap(enemyAttack.spawnX + counter.deltaX)`、護衛候補の発射列は `wrap(myAttack.spawnX + escort.escortDeltaX)` と一致する(基準は現在位置 `x` ではなく発射位置 `spawnX`)
- [ ] 発射できる候補が1件も無い、または WAIT が選ばれた間は、トークンを貯め続ける
- [ ] 選択に乱数を使う箇所(候補の発射列サンプリング)は `Match.seed` の擬似乱数を使い、同じシードなら同じ試合になる。特徴計算・スコア計算自体は乱数を使わない(完全決定論)
- [ ] 予約した迎撃・護衛が実際に発射されること(握りつぶし率 0%)。`commitments`/`projectedTokens`/`releaseExpiredCommitments` による予約発射のトークン確保は v5.2 から維持する
- [ ] 同一seed・同一 `weights` なら試合結果が完全再現する

**学習する方策パラメータ**(`data/policy.json`)

旧11次元の方策パラメータ(`fireThreshold`/`reserveTokens`/`defendBias`/`escortBias`/`attackPref[3]`/`selfDestructBias`/`selfDestructRemainingTicks`/`pollutionDestructWeight`/`attackAvoidBias`)は**すべて廃止**され、**24要素の `weights`(線形評価器の重み)ひとつ**に統合された。24特徴それぞれの名前・範囲・定義は契約書 §5 の凍結表が唯一の定義(本書では複製しない)。

**Reference League**(`src/reference-policies.js`。契約書 §6)。学習しない固定4方策で、`generateActions` を共有しスコア関数だけ差し替える。CEM の fitness の半分(各12.5%)と、`evaluate-policy.mjs --mode final` の対戦相手に使う。

| 方策 | 規則 |
|---|---|
| `ATTACK_ONLY` | 即時の attack FIRE のみ採用。妨害・自爆は不採用 |
| `CHEAP_SPAM` | 即時 attack FIRE のうち `cost` 最小のものを採用 |
| `SAVE_AND_BURST` | 保有トークンが `BURST_THRESHOLD`(=20)未満なら WAIT。以上なら `ATTACK_ONLY` と同じ |
| `DEFEND_HEAVY` | `source === 'counter'` の FIRE(迎撃由来)があればそれを採用。無ければ `ATTACK_ONLY` と同じ |

**学習方法**: CPU同士の自己対戦 + CEM法(交差エントロピー法。**24次元 対角ガウス**)。`population=80` / `elite=16` / 1個体40試合(self-play 20 + Reference League 4種×5) / `minGenerations=20` / `maxGenerations=60`。fitness = self-play勝率50% + Reference League平均勝率50%(**特定戦術の使用回数は fitness に入れない**。分析ログとしてのみ記録する)。5世代ごとに held-out validation(400試合/候補)を行い、20世代以降 plateau(直近2checkpointの改善が1ポイント未満)で early stop できる。最終世代の mean を無条件採用せず、`mean`/`bestValidation`/直近世代ベストの複数候補を固定シードで再評価して採用する。`worker_threads` で並列化し、乱数はメインスレッドだけが持ち結果は投入した添字順に集約するので、ワーカー数を変えても出力は一致する。

**実測値は「v6 の学習後検証・バランス実測」節**(第8章のあと)にある。

⚠️ **`--mode bench` を全0の重みのまま実行しても意味のある値にならない**(全 Action のスコアが0点で `score(WAIT)=0` と同点になり WAIT が勝つため、1発も撃たない試合の速度を測るだけになる。`evaluate-policy.mjs` 自身のコメント参照)。実行順は
`node scripts/train-policy.mjs --quick --out <tmp>`(軽く学習した重みを作る)→
`node scripts/evaluate-policy.mjs --mode bench --policy <tmp>`(§28。本学習**前**の性能計測)→
`node scripts/train-policy.mjs`(本学習)→
`node scripts/evaluate-policy.mjs --mode final`(§26。リーグ4種×500試合+旧CPU 1,000試合)。

#### 機能9：ハイウェイ探索(オフライン。v5 で追加)

`scripts/generate-templates.mjs` が実行するテンプレート生成パイプラインの一部。プレイヤー・CPU の実行時ロジックではなく、`data/templates.json` を作るための開発時処理。

**ハイウェイ検出の2段構え**

- [ ] 高速フィルタ(`src/search/highway-trajectory.js` の `detectHighwayFromPath`)が、軌跡(位置+向き)だけから周期性を検出する。MAP-Elites 探索中の全候補にこれだけを適用する
- [ ] 厳密確認(`src/search/highway-fingerprint.js` の `verifyHighwayStrict`)が、アリ座標を原点とした近傍セルの正規化 fingerprint を用いて、高速フィルタで採用された候補だけを盤面込みで再検証する
- [ ] `highway.trajectoryPeriodic` と `highway.fingerprintVerified` は独立した2つの boolean で、MAP-Elites 探索中(アーカイブ挿入・記述子計算)は前者だけを、最終テンプレート選抜(9×9)は後者だけを使う。混同しない
- [ ] `src/search/highway-detector.js` はこの2モジュールを再エクスポートするだけのファサードである

**Seed Distillation**(§10〜§24 相当)

- [ ] 検出済みハイウェイについて、形成時点(`formationStep` およびその後の安定周期開始位置)の局所盤面を crop 半径を段階的に広げながら切り出す(`src/search/seed-distillation.js` の `captureFormationSnapshot`)
- [ ] 切り出した種セルから走らせ直し(replay)、元のハイウェイと同じ `period`/`driftX`/`driftY` を `HIGHWAY_MIN_CYCLES`(5)周期以上再現することを確認する(`replaySeed`)。再現しなければその crop 半径・snapshot 位置を棄却する
- [ ] 再現した種セルを、アリから遠い順に貪欲削除して圧縮する(`src/search/seed-compression.js` の `compressSeed`)。削除後も再現性が保たれる場合のみ削除を確定する
- [ ] 圧縮後の種がゲームで採用可能かを判定する(`gameUsability`)。条件: セル数 ≤ `MAX_CELLS`(16)、`|dx|`/`|dy|` ≤ `TEMPLATE_CELL_RADIUS`(8)、かつ dy の広がりが `ZONE_DEPTH` に収まる `antY` が存在すること
- [ ] 採用可能な蒸留 genome(`origin: 'distilled'`)は、通常の genome と同じ扱いで MAP-Elites の第1アーカイブへ再投入される(特別扱いしない)
- [ ] 蒸留の試行数・成功数・成功率・formationStep 短縮量・セル数の変化・蒸留前後の viable 件数が `data/search-report.json` に記録される(`src/search/search-report.js` の `buildSearchReport`)

**並列化と決定論**

- [ ] `scripts/generate-templates.mjs` は `scripts/lib/worker-pool.mjs`(`worker_threads` の固定サイズプール)を使って genome の評価を並列化する
- [ ] 乱数(genome 生成・親選択・突然変異)は**メインスレッドだけ**が持ち、ワーカー(`scripts/lib/search-worker.mjs`)は渡された genome を評価して返すだけの純粋関数である
- [ ] 評価結果は**完了順ではなく投入した添字順**にアーカイブへ挿入される。この2条件を満たす限り、ワーカー数(`--workers`)を変えても `--seed` 固定なら出力がバイト単位で一致する

### テンプレート選抜基準(`generate-templates.mjs` 段階2の合格ライン)

9×9 を選ぶときの必須条件と目標。**v5.1(256×256盤面・寿命20,000)でこれを満たす組み合わせが存在することを確認済み**(選抜スコア +189、必須条件すべて OK)。

| 基準 | 値 | 種別 |
|---|---|---|
| カウンターを1つも持たない攻撃 | **0件** | 必須(1件でもあれば勝ち確定になる) |
| 1件も止められない妨害(死に札) | **0件** | 必須 |
| 攻撃1件あたりのカウンター種数(**3種中**) | **1〜3種** | 目標。⚠️ **v5.5 で分母が9→3に変わったための構造的な読み替え**(旧: 9種中2〜4種)。数値を範囲に収めるための緩和ではない。「0種(カウンター無し)」の禁止は `BALANCE.attacksWithoutCounter = 0` が引き続き必須条件として担保する。v5.1 は同梱 counterTable で86エントリ・攻撃9件すべてがカウンターを持つ |
| 妨害1件あたりのカバー数(9件中) | 2〜4件 | 目標(v4実測は2〜3件。**v5.1実測は coverage 33〜78%**、死に札0件) |

## 8. 決定事項(意図的な割り切り)

すべて実測に基づく。詳細は [../REVIEW.md](../REVIEW.md) 付録C。

- ~~**RRL(3色)を採用し古典ラングトンのアリ(RL)を見送った**~~ **(v4 で解消)**: RL はハイウェイ形成に9,976ステップかかり、120×60・寿命2,400の設計では届かなかった。v4 で**ルールをテンプレートごとに持つようにしたため「1つを採用する」という決定自体が消えた**。RL(=`'RL'`, 2色)は選べるが、形成9,976ステップは寿命2,400の外なので実測の得点率は 0.00% で、選抜には残らない
- **寿命(最大ステップ数)で「ハイウェイ以外」を落とす**: 得点には88列の横断が必要で、カオス的運動は正味変位がほぼゼロなので原理的に届かない。実測でも、寿命の余裕を1.05倍から2.5倍まで変えても得点弾のHW割合は98%のまま変わらなかった(＝非ハイウェイは寿命を緩めても届かない)
- **得点条件は「敵の配置可能帯に入った瞬間」**: 「帯を突破して奥の端まで」にすると防御ブロックが効くようになるが(実測で64%減)、**妨害アリという別の防御手段を採用したため不要**と判断した
- **配置ブロックによる防御は機能しない**: 実測で、敵の配置可能帯に80個のブロックを置いても得点率は下がらなかった(アリは帯の1列目に触れた瞬間に得点するため)。防御はブロックではなく妨害アリで行う
- **盤面は完全には元に戻らない**: 複数アリが干渉するため。それが駆け引きの中心なので許容し、汚染度をバランス指標で監視する
- **テンプレートは妨害込みで評価し、攻撃と妨害を共進化させて生成する**: 空盤面だけで評価すると「妨害に強い配置」を選べない。実測では、攻撃側がカウンター数を最小化する探索をすると**わずか120回の評価(14秒)で、120種の妨害手札に一度も止められない攻撃が見つかる**。放置すると勝ち確定の弾ができてしまう。一方、防御側も3,000回程度の探索でその攻撃へのカウンターを必ず見つけられるので、交互に回せば健全な均衡に落ち着く(実測: 4ラウンドでカウンター密度が中央値3.6%→1.0%に下がり、カウンターを持たない攻撃は0件のまま安定)

### v4 で追加した決定事項

- **異種ルールの衝突は「余りとして解釈する」で吸収する**: 盤面は1枚を共有するのに色数がアリごとに違うため、ルールにない色を踏むことが必ず起こる。`board[i] % ant.colorCount` の1行で吸収し、この状態空間の圧縮そのものを干渉として扱う。分岐を増やさないので決定論性が保たれ、`engine.js` の1ステップ処理が単純なまま済む

- **ハイウェイの向きはルールでは変えられない(実測)**: 「ルールを変えれば横方向ハイウェイが作れる」という当初の想定は**実測で否定された**。ルール長2〜6の全114ルール × ランダム初期配置200通り(22,800試行)で検出した3,520件のハイウェイは、**並進ベクトルが例外なく (±1,±1) の45度**。4方向の違いは発射時の向きから来る。ルール選択が効くのは**速度(0.0192〜0.0556 列/ステップ)・形成ステップ(38〜25,952)・色数(干渉の非対称性)**である

- **探索の定義を「縦ハイウェイを探す」から改めた**: v4 の探索が解いている問題は、正確には次である。
  > **一般化ラングトンのアリの (ルール × 初期配置) 空間から、有限寿命・ラップ境界条件のもとで敵陣へ到達可能な周期移動体を探索する**

  「縦ハイウェイを主目的とする」という当初の研究仮説は、左右がラップする以上ゲーム上の必要条件ではない(45度でも巻きつきながら到達する)。上の定義がゲームと MAP-Elites 探索の双方に一致する。

- **⚠️ ゲーム候補の条件を正式に置き換えた**:

  | | 条件 |
  |---|---|
  | 旧 | `driftX === 0 && driftY > 0` |
  | **新** | **`GAME_PROJECTILE_LIFE` 以内に敵陣へ到達すること** |

  `direction` は**採否条件ではなく純粋な Behavior Descriptor** として扱う。第1アーカイブは `(direction, speed, formationTime, cost)` のままでよく、ゲーム投影の段階だけを `reachesEnemyZoneWithinLife === true` にする。

  ⚠️ 判定に **ETA の近似式を使わない。** 45度ハイウェイが左右にラップしながら進む場合、実効的な縦方向速度 `v_y = |Δy| / T` が十分なら弾として成立するので `ETA ≒ 残り縦距離 / |v_y|` は目安になるが、transient(形成前の非周期区間)とラップがあるため誤差が出る。**最終判定は必ず直接シミュレーションで敵陣到達を確認する**(`src/engine.js` の `simulateSolo` を実ゲーム条件で走らせる)。

  この緩和の根拠:
  - ルール長2〜16・セル状態自由の探索空間でも、`driftX === 0` のハイウェイは検出7,680件中**1件**(0.013%)しか出ない
  - しかもその1件(`RLRLRLLRRRLLRLLR`・16色・周期468・drift (0,-8)・形成1,192ステップ)は89行渡るのに約6,400ステップ必要で、**寿命2,400の2.7倍**。ゲームでは使えない
  - **左右がラップするので45度ハイウェイでも敵陣に到達できる。** 実ゲーム条件でランダム genome の1.81%が実際に得点する

  > 📌 **`driftX === 0` の希少性そのものは実験結果として保存する価値がある。** 「ルール長2〜16・セル状態自由の空間で、純粋な縦ハイウェイは7,680件中1件(0.013%)しか存在せず、その1件もゲーム寿命の2.7倍を要して到達不能」という測定は、**なぜゲーム採用条件を緩和したのかを説明する一次資料**である。`data/search-archive.json` には向きによらず全ハイウェイを保存し、この分布を後から再確認できるようにする(§23)。

- **探索評価とゲーム評価を別の盤面で走らせる**: §7 は「探索20,000ステップ / ゲーム採用2,400ステップ」と2つのレジームを分けているが、探索も実ゲーム盤面(60×120)で走らせると**アリが上下端で死ぬため20,000ステップに到達しない**(実測: 到達率 **11.6%**、軌跡長の中央値 1,889、20.3%が200ステップ未満)。短い軌跡に5周期の検出をかけると**過渡的な直進を大量に偽陽性としてハイウェイ判定してしまう**(§27 の false positive rejection がまさにこれ)。実害として、記述子の `direction` の **34%が `'N'`(純粋な縦)** になっていた — 独立実測では45度しか存在しないのに。
  したがって**探索評価だけ `C.SEARCH_BOARD_HEIGHT`(=4,096) の仮想盤面**(上下端なし・得点判定なし・左右ラップは実ゲームと同じ)で走らせる(`src/engine.js` の `simulateSearch`)。ゲーム評価は従来どおり `simulateSolo` を実ゲーム盤面で使う。
  修正後の実測: 20,000ステップ到達率 **100%**、`'N'` は **0.2%** まで低下し、並進ベクトルは対角 (±1,±1)/(±2,±2) が支配的になった。回帰フィクスチャ(`LEGACY_RULE` で `formationStep=38` / `period=18`)は不変。
  ⚠️ 代償として評価コストが約5.7倍(20,000 genome で 8.7秒 → 50秒、約400 genome/秒)になった。探索予算はこのスループットで見積もること。

- **⚠️ 攻撃アリの寿命を 2,400 → 3,600 に引き上げた(弾速の多様性を物理的に成立させるため)**:
  中間地帯88行を渡るのに必要なステップ数は速度クラスごとに `LLR`=1,621 / `RRRRL`=3,096 / `RRRLLL`=3,445 / `RRRRRL`=3,824 / `RL`=14,560 で、**寿命2,400 では `LLR` 系しか物理的に届かない**。
  実際、寿命2,400 で生成した攻撃9種は宣言ルール長が 3/6/9/14/15 とばらついていたのに、**実効色数は3か6、ハイウェイ署名は9種すべて period=18 / drift=(±1,±1) の1種類だけ**だった。`LLRLLR` は `rule[s % 3]` が `LLR` と同じなので**力学的に同一**で、長いルールの末尾は一度も踏まれない死にコードになる。つまり「ルールを選んで撃つ」という v4 の主目的が成立していなかった。
  3,600 にすると上位3クラス(`LLR` / `RRRRL` / `RRRLLL`)が届き、**到達時間に 13.5秒〜28.7秒 の差**が生まれて読み合いの軸になる。
  ⚠️ 代償として「寿命がハイウェイ以外を落とすフィルタ」という v3 からの設計原則が弱まる。`highwayShareOfScoring`(95%以上)を必ず再測定すること。

- **ルールは原始形(primitive root)に正規化する**: `LLRLLR` のように短いルールの繰り返しになっているルールは、`rule[s % 元の長さ]` が同じなので元のルールと**完全に同じ挙動**になる。多様性の判定を `rule.length` で行うと、こうした等価ルールを「別物」と数えてしまい、選抜が多様性を偽装できてしまう(実測でこれが起きた)。したがって:
  - genome のルールは**最小の繰り返し単位に還元**してから扱う
  - 9×9 選抜の多様性基準は `rule.length` ではなく**ハイウェイ署名(周期・並進・形成ステップ)**で測る。プレイヤーが実際に体験するのは弾速と到達時間であって、ルール文字列の長さではない

- **⚠️ `FIRE_TIMINGS` は `ATTACK_LIFE` から導出する(固定リストにしない)**: v3.1 の `[0, 150, ..., 1350]` は寿命2,400 用に決めた格子で、v4 で寿命を3,600 に上げたときに据え置いたため、**飛行後半をカバーする迎撃タイミングが存在しなくなった**。妨害は寿命400(v4 の120ステップ/秒で≒3.3秒)なので1,350 に撃つとステップ1,750 には消えているが、低速クラスの弾の到達は 2,316〜3,458 ステップである。
  結果として「**低速の弾はどれ1つとしてカウンターを持てない**」状態になり、必須条件「カウンターを持たない攻撃=0件」によって低速弾が**構造的に選抜不可能**になっていた。目標「ハイウェイ署名3種類以上」が達成できなかった真因はこれ。
  実測(低速署名の viable 個体8件 vs 同じ妨害候補23件): 旧格子(最大1,350)でカウンターを持てたのは **0件/8件**、新格子(最大3,000)では **7件/8件**。成功した迎撃タイミングは**すべて1,650〜3,000**、つまり旧格子の完全に外側だった。
  → `FIRE_TIMINGS` は `0` から `ATTACK_LIFE - 600` まで150間隔で生成する。**寿命を変えたら格子も自動で追随する**ので、この失敗は再発しない。
  ⚠️ **この「間隔を寿命に比例させる」設計は v5.1 で部分的に破綻した**: `ATTACK_LIFE` が20,000まで伸びると比例間隔のままでは候補が約50点に増え、カウンター表(直積)の計算コストが約3時間に膨らんだ。v5.1 では「本数14固定・間隔の方を寿命に比例させる」方式に置き換えている(詳細は下の「v5.1 で追加した決定事項」)。

- **ハイウェイ検出を正式に2段構えにした**:

  | | 検出方式 |
  |---|---|
  | 旧 | 全候補に正規化 fingerprint |
  | **新** | **軌跡の周期性による高速検出 → 採用候補のみ fingerprint 厳密検証** |

  MAP-Elites は評価回数が支配的なので、毎ステップの近傍ハッシュ化を全候補にかけるのは成立しない。パイプラインは次のとおり:

  ```text
  全 genome
     ↓ 位置 + 向きの周期検出（高速フィルタ）
  highway候補
     ↓ 5周期以上の連続一致
     ↓ ゲーム到達判定（寿命内に敵陣へ到達するか）
  有望候補のみ
     ↓ local fingerprint
  厳密 highway 確認
  ```

- **⚠️ `highway.detected` を単一の boolean にしない**: **軌跡の周期性はハイウェイの十分条件ではない**(位置と向きが周期的でも、周囲のセル状態が同じ構造を再生産しているとは限らない)。1つの boolean にまとめると、高速フィルタの近似が最終選抜まで素通りする。したがって2つに分ける。

  ```ts
  highway: {
    trajectoryPeriodic: boolean,   // 高速フィルタ(軌跡の周期性)を通った
    fingerprintVerified: boolean,  // 近傍状態の fingerprint による厳密確認を通った
    period: number,
    driftX: number,
    driftY: number,
    verifiedCycles: number,
    formationStep: number,
    speed: number,
  }
  ```

  使い分けを固定する。

  | 場面 | 使う値 |
  |---|---|
  | MAP-Elites 探索中(アーカイブ挿入・記述子計算) | **`trajectoryPeriodic`** |
  | 最終テンプレート選抜(9×9) | **`fingerprintVerified`** |

  探索中に厳密検証をかけるとスループットが破綻し、最終選抜で高速フィルタのまま通すと偽陽性が製品に混入する。この境界を跨がないこと。

- **PC・スマホ両対応を必須要件にした**: v3.1 でスコープ外にしていたモバイル対応を必須へ格上げした。v4 時点では盤面が 60×120 の縦長(1:2)で、広幅では盤面＋操作パネルの2カラム、狭幅では1カラムへリフローする方針だった。⚠️ v5 で盤面が 256×256(正方形・1:1)になったため、この縦長前提のレイアウト方針は再検討が必要(🚧 未着手。デザインの唯一の正は [../DESIGN.md](../DESIGN.md) と `src/tokens.css` だが、本ドキュメント更新の範囲では `DESIGN.md` は未確認・未更新)

- **セルの描画で「状態」と「陣営」を直交させた**: セルは状態0..15 と「最後に触れた陣営」の2情報を持つ。32色を用意するのではなく、**色相=陣営(藍=side1 / 朱=side2)・濃度=状態値**の2軸に分けた。`match.lastToucherSide` がこの色相側の入力になる。`lastToucher` によるクリーンアップ判定のロジックは変更していない

### v5 で追加した決定事項

- **盤面を 60×120 → 256×256(正方形)に拡大した**: より複雑なハイウェイと戦略が成立する余地を作るための設計判断。中間地帯が88行→192行になり横断距離が2.2倍になったため、寿命を3,600→6,000に、ステップ速度を120→300に引き上げて体感時間(11.6〜19.7秒)をv4と同水準に維持した(⚠️ **寿命・ステップ速度とも v5.1 でさらに更新**。寿命20,000・670ステップ/秒が確定値。詳細は下の「v5.1 で追加した決定事項」)。盤面セル数が7,200→65,536になったことで `engine.js` の全盤面走査(クリーンアップ)が支配的コストになったため、`ant.touched` によるインデックス走査に置き換えた(挙動は同値。`test/engine.test.js` に回帰テストあり)

- **得点ゲートを導入した**: 盤面を256列に広げ、かつ発射列を可変にしたことの帰結として、守る側は256列すべてを警戒しなければならず迎撃が成立しなくなる。得点を中央192列に限ることで「門を守る」という防衛目標を作り、`attacksWithoutCounter = 0`(必須条件)を満たせる幅に戻した。左右32列ずつは得点しない「壁」になる

- **発射列(antX)を可変にした**: 左右がトーラスである以上、x方向の平行移動は力学の厳密な対称性であり、同じテンプレートをどの列から撃っても軌道・周期・並進・形成ステップは変わらない。テンプレートを genome と同じ「アリからの相対座標」表現に揃えることで、Seed Distillation が生成する種(アリ周囲の局所セル)とも表現が一致する利点がある。帰結として `identifyTable` のキーが `"antX,antY,antDir"` → `"antY,antDir"` になり、`counterTable`/`escortTable` は絶対列ではなく `deltaX`(妨害の発射列−攻撃の発射列)の表になった

- **配置マスをアリ近傍(`TEMPLATE_CELL_RADIUS`=8)に限定した**: 盤面が256列になると配置帯は256×32=8,192マスになり、配置帯全体に一様に16マス撒くと密度0.2%になってアリが配置マスを一度も踏まない(=genomeの初期配置部分が無意味になる)ことが実測で分かった。アリの近傍に限定して撒くことで初期配置が軌道に効くようにした

- **`ATTACK_LIFE` を「探索をやり直さずに後から決められる」構造にした**: 探索中のゲーム射影は `ATTACK_LIFE` ではなく `GAME_LIFE_SEARCH_CAP`(導入時は12,000固定)で走らせ、個体ごとの実到達ステップ数(`arrivalStep`)を記録する。探索後に `scripts/tune-attack-life.mjs` で `arrivalStep` の分布を掃引し、「viable件数/到達時間の分散/速度クラス被覆」から `ATTACK_LIFE` を決める。✅ **v5.1で確定**(`ATTACK_LIFE`=20,000。詳細は下の「v5.1 で追加した決定事項」)

- **Seed Distillation を導入した**: 通常の genome は「初期配置→transient→formationStep→highway」という流れを持ち、transient がそのままゲームでは「発射から弾が仕上がるまでの遅延」になる。発見済みハイウェイが形成された時点の局所盤面を切り出し、そのハイウェイ状態を直接開始できる有限初期配置(種)へ逆変換することで、「発見しやすいが形成が遅いハイウェイ」と「ゲームで即座に使えるハイウェイ種」を分離して探索する。蒸留 genome(`origin: 'distilled'`)は通常の個体と同様に MAP-Elites アーカイブへ再投入する(特別扱いしない)

- **ハイウェイ検出を `highway-trajectory.js`(高速フィルタ)と `highway-fingerprint.js`(厳密確認)の2モジュールに正式に分割した**: 探索評価と厳密検証は計算コストが大きく異なるため、ファイルを分けて責務を明確にした。`highway-detector.js` は既存の import 元を壊さないための再エクスポート専用ファサードとして残す

- **探索を `worker_threads` で並列化し、決定論を依存関係で担保した**: 乱数(genome生成・親選択・突然変異)をメインスレッドだけに置き、ワーカー(`scripts/lib/search-worker.mjs`)は「渡された genome を評価して返すだけの純粋関数」にした。結果は完了順ではなく**投入した添字順**にアーカイブへ挿入する。この2条件を守るかぎり、ワーカー数(`--workers`)を変えても `--seed` 固定で出力がバイト単位で一致する

- **`src/template.js` を独立モジュールとして切り出した**: `src/cpu.js` は `src/engine.js` を import してはいけない(実行時のシミュレーション探索をしないことを依存関係で担保するため)。一方、発射列が可変になったことで CPU もプレイヤーUIも「相対テンプレート→絶対座標」の変換が要る。これは純粋な座標計算でありシミュレーションではないため、`engine.js` から独立させて `engine`/`cpu`/`app`/`scripts` が同じ実装を共有できるようにした

### v5.1 で追加した決定事項

- **`ATTACK_LIFE` を暫定値6,000から確定値20,000にした**: 1,014万評価の探索アーカイブを `scripts/tune-attack-life.mjs` で掃引して決めた。弾種の多様性は寿命に対して単調に増える(実測: 寿命6,000→viable 49件・ハイウェイ署名2種 / 7,500→65件・5種 / 9,000→128件・9種 / 12,000→356件・18種)。上限を決めるのは物理ではなくテンポで、1発の滞空最大時間 `ATTACK_LIFE / STEPS_PER_SECOND`(=20,000/670≒29.9秒、240秒試合の約1/8)を基準に選んだ。「寿命がハイウェイ以外を落とすフィルタ」という設計原則は、乱数候補4,000件で寿命6,000〜12,000のいずれでも敵陣到達弾のハイウェイ割合が100.0%であることを確認しており、**寿命を延ばしても壊れない**(193行の正味の縦方向変位はカオス的運動では到達不能なため)

- **`STEPS_PER_SECOND` を 300 から 670 に引き上げた**: 到達時間の**比**(最速弾3,471step / 最遅弾20,000step = 5.8倍)はステップ速度に依存せず、変わるのは絶対時間だけ(300なら最速11.6秒/最遅66.7秒、670なら最速5.2秒/最遅29.9秒、900なら最速3.9秒/最遅22.2秒)。900は最速弾が3.9秒で着弾し、「識別→迎撃札を選ぶ→発射列を合わせる→撃つ」に必要な時間(CPUの判断周期1秒あたり)が足りない。670 は最速弾5.2秒を確保できる下限として選んだ

- **`GAME_LIFE_SEARCH_CAP` を固定値12,000から `ATTACK_LIFE` に連動する値に変更した**: `src/config.js` で `GAME_LIFE_SEARCH_CAP = ATTACK_LIFE` と定義し、以後 `ATTACK_LIFE` を変えても手直しなく追随するようにした。副作用として、保存済みの `arrivalStep` は「保存した当時の `GAME_LIFE_SEARCH_CAP`」までしか記録されていないため、キャップより長い寿命へ再射影するときはアーカイブの genome を再評価する必要がある。`scripts/generate-templates.mjs --resume-archive` がこれを行う(実測: 1,407件の再評価が2.1秒で完了し、攻撃候補が49件/署名2種 → 360件/署名18種になった)

- **`FIRE_TIMINGS` の導出方法を「秒数比例の間隔」から「本数14固定」に変更した**: `ATTACK_LIFE` を20,000に伸ばすと比例間隔のままでは候補が約50点に増え、カウンター表((攻撃×妨害×deltaX×タイミング)の直積)の計算量が3.8倍(約3時間)に膨らみ、最終選抜が探索本体より長くなってしまう。守る側にとって意味があるのは「妨害の寿命ぶんズラした別の手」なので、候補の本数(`FIRE_TIMING_COUNT`=14)を固定し、間隔(`FIRE_TIMING_INTERVAL`)の方を寿命に比例させる表現に変えた。間隔が `DECISION_INTERVAL_STEPS` の倍数になった場合は50ずらして避ける

- **`ARCHIVE2.speedClassBins` を `[0.04, 0.048, 1.0]` から `[0.025, 0.040, 1.0]` に更新した**: `ATTACK_LIFE` の確定に伴い到達可能な実効縦速度 `v_y` の下限が `193行 / ATTACK_LIFE` = 0.0097 に変わった(旧寿命6,000では0.0327)。上限は実測で最速のハイウェイ 1/18 ≈ 0.0556 のまま。0.0097〜0.0556 をほぼ3等分する位置に境界を切り直した

- ~~**`DISRUPT_LIFE`(=1,000)は据え置いた**~~ **(v5.3 で撤回。[v5.3 の決定事項](#v53-で追加した決定事項)参照)**: `STEPS_PER_SECOND` の変更で実時間は3.3秒→1.49秒になったが、この定数が担保しているのは実時間ではなく**到達距離**という空間的性質(最速クラスでも約56行しか進まず、192行ある中間地帯の1/3までしか届かない)であり、ステップ速度に依存しない。⚠️ **この「寿命で到達距離を担保する」考え方自体が v5.3 で誤りと判明した**(担保が成り立つのは寿命3,474ステップ未満のときだけで、しかもテンプレートを再生成すると前提が崩れる)。v5.3 は `DISRUPT_MAX_LOCAL_Y` で空間そのものを縛る方式に変え、寿命は6,000に引き上げた。ただし `ATTACK_LIFE` との比が 9:1(v4)→20:1(v5.1) に広がったため、迎撃の時間窓が相対的に狭くなっていないか `counterDensityMedian`/`attacksWithoutCounter` を🚧再測定して確認すること

### v5.4 で追加した決定事項

- **妨害の照準を事前計算テーブルに戻した**: 迎撃列 = `wrap(敵攻撃の spawnX + counterTable.deltaX)`、護衛列 = `wrap(自攻撃の spawnX + escortTable.escortDeltaX)`。基準は**現在列 `x` ではなく発射列 `spawnX`**(`deltaX` が「妨害の発射列 − 攻撃の発射列」として事前計算されているため)。⚠️ **`deltaX` は候補ごとに違う**ので、発射列の計算は候補走査ループの**内側**で行う(呼び出し元が単一の列を先に決めて渡すと、候補ごとの照準情報を捨てることになる)

- **`selfDestructAgeFrac`(寿命の消化割合)を `selfDestructRemainingTicks`(残り判断tick数、整数1〜10)に置換した**: 割合だと種別ごとに絶対時間の意味が変わる(寿命20,000の攻撃と6,000の妨害で同じ0.9でも残りステップが2,000と600)うえ、「あと何回撃ち直せるか」という意思決定に直結しない。tick は判断周期 `DECISION_INTERVAL_STEPS` そのものなので直結する。⚠️ 比較が `>=` から `<=` に反転したので、方策未指定時の既定値も `?? 1` から **`?? 0`**(=候補ゼロ＝自爆しない)に反転させる必要がある

- **自爆の判定順を「候補を数える → 候補が居るときだけ抽選」に変えた**: 候補ゼロでも乱数を引いていると、方策が違っても乱数の進み方が同じだけ揃ってしまい CRN での比較がぼやける

- **方策ベクトルを18次元 → 17次元にした**: `disruptAimOffsetFrac` を削除、`selfDestructAgeFrac` → `selfDestructRemainingTicks`。CEM 内部の平均・標準偏差は浮動小数のまま保持し、方策へデコードするときだけ整数へ丸める(このパラメータのために離散最適化は導入しない)

- **`src/cpu.js` に副作用のない観測フック `options.observe` を追加した**: 迎撃も護衛も engine から見れば同じ `disrupt` アクションなので、**判断の「意図」は action の形からは復元できない**。§11 が要求する「迎撃の発射数」と「護衛の発射数」の内訳を測るために、意図だけを外へ出す。既定は no-op で乱数も消費しないため、渡さなければ試合の再現性は完全に同じ

⚠️ **`winRateVsRandom` はバージョンをまたいで比較してはいけない**(v5.3 の 1.000 と v5.4 の 0.868 は別物の測定)。固定アンカー `RANDOM_POLICY` 自身が v5.4 で `deltaX` 照準に変わっており、基準が動いているため。

⚠️ **迎撃は「効果があるが高い」のではなく、そもそも効果が測れない。** v5.4 で対照群つきで測ったところ:

| | 件数 | 得点率 |
|---|---:|---:|
| 迎撃を割り当てられた敵攻撃アリ | 101 | **55.4%** |
| 迎撃されなかった敵攻撃アリ | 4,337 | **53.5%** |

差は **−2.0ポイント**(迎撃された方がわずかに得点率が高い)。n=101 の標準誤差が約4.9ポイントなので、**迎撃が得点を減らしている証拠は無い**。
⚠️ 「迎撃成功率44.6%」という数字を単独で出してはいけない。これは対象の得点率の裏返しにすぎず、比較対象(迎撃しなかった弾の得点率)を並べて初めて意味を持つ。

⚠️ **そのうえで迎撃はトークンを大量に食う。** アンカーの `defendBias` だけを振ってアンカー自身の内訳を測ると(200試合・CRN):

| アンカーの `defendBias` | 攻撃/試合 | 迎撃/試合 | アンカー得点 | 相手得点 | 学習済み方策から見た勝率 |
|---:|---:|---:|---:|---:|---:|
| 0.0 | **10.54** | 0.00 | **4.37** | 3.33 | **0.315** |
| 0.5(現行の `RANDOM_POLICY`) | 4.61 | 14.87 | 2.35 | 4.75 | 0.900 |
| 1.0 | 2.09 | 19.88 | 1.54 | 4.96 | 0.998 |

(対照: 相手も学習済み方策のときの勝率 0.487 ≒ 0.5 なので結線は正常)

迎撃を有効にすると**自分の攻撃が 10.54 → 4.61 → 2.09 へ激減し、自分の得点も 4.37 → 1.54 に落ちる一方、相手の得点は 3.33 → 4.96 に上がる**。
機構は**トークンの名目コストが支配的**である: 迎撃 14.87 回の代わりに攻撃 5.93 回を失っており(妨害は攻撃より安いので回数比が1対1にならない)、予約の平均拘束時間は約3,034ステップ ≒ 判断4.5回ぶんで副次的な寄与にとどまる。
⚠️ **「相手の得点が上がる」理由は未特定。** 攻撃数・自分の得点・盤面の綺麗さがこの掃引では同時に動くので、因果は切り分けられていない([未決定事項](#v54-で新たに洗い出した未決定事項)参照)。したがって:

1. **CEM が `defendBias` を 0 に収束させたのは正しい判断**であって、学習の失敗でも照準の不備でもない
2. **固定アンカー `RANDOM_POLICY`(`defendBias=0.5`)は「半分の確率で自分を弱くする」相手**なので `winRateVsRandom` は実力を過大評価する。迎撃しないだけの無学習方策に、学習済み方策は **31.5%** しか勝てない
3. fitness の半分がこのアンカーとの勝率なので、**学習は「迎撃で自滅する相手を叩く」方向に部分的に最適化されている**

これは v5.4 の変更が生んだ問題ではなく、v5.4 で初めて**測った**問題である(v5.3 までは迎撃の照準自体が機能していなかったので、「照準が悪いのか」「迎撃自体が無駄なのか」を切り分けられなかった)。対処は[未決定事項](#v54-で新たに洗い出した未決定事項)参照。

### v6 で追加した決定事項

すべて [action-centric-contract.md](action-centric-contract.md) が確定契約。ここでは設計判断の要旨と、契約書 §11 が明記する「仕様書に書かれていない判断」5点をまとめる。

- **CPU に与えるのは「何が合法か・何を観測できるか」までで、「何を選ぶべきか」は与えない**。`generateActions` は合法性・トークン会計・`MAX_FLYING`・候補圧縮だけを行い、「敵が来たから迎撃を優先する」「汚れていない列を選ぶ」といった戦術判断を一切埋め込まない。判断の善し悪しは24次元の特徴が表現し、線形評価器の重みが学習する
- **Action 型を WAIT / FIRE / SELF_DESTRUCT の3種に絞った**。ATTACK / DEFEND / ESCORT という型を作らないことで、「迎撃」「護衛」は人間が事後的に解釈するラベル(`source` フィールド。ログ専用)に過ぎなくなり、CPU の選択規則からカテゴリの概念そのものを除去した
- **自爆候補の事前フィルタ(年齢・残寿命・盤面汚染度)を廃止した**。飛行中の自軍アリは全部が候補になり、年齢は特徴(#20 `destructAge`)として評価器に渡るだけにした。「若いアリを自爆させない」という判断も学習結果として許容する
- **攻撃 FIRE を得点ゲート内だけに限定しない**。得点ゲート外(`scoreReachability=0`)の発射列も候補に残すことで、攻撃アリを妨害・護衛・囮・盤面操作として使う戦略を方策表現から締め出さないようにした
- **`counterTable`/`escortTable`/`identifyTable` を「候補生成情報」へ降格した**。「その表由来だから優先する」という選択規則を廃止し、`counterTable.successRate` を24特徴から外した(候補の列挙順を決めるためだけに使う)
- **1判断=1アクションにした**。旧実装の「自爆してから攻撃」「攻撃と同時に護衛を予約」という抱き合わせ処理は、単一 Action を選ぶという設計に反するため廃止した

契約書 §11 が明記する、仕様書に書かれていない実装判断5点:

1. **発射列のサンプリング**: 得点ゲート内から `ACTION_ATTACK_GATE_SAMPLES`(4列)・ゲート外から `ACTION_ATTACK_OFFGATE_SAMPLES`(2列)を match RNG で一様にサンプルする。旧 `chooseAttackColumn`(`attackAvoidBias`)の汚染回避ヒューリスティクスは戦術の直接教示にあたるため移植しない
2. **1判断=1アクション**の採用そのもの(上記)
3. **`lastToucherSlot` の導入**: ownership map の増分更新でアリIDからスロットを引く Map 参照をホットパス(`stepAnt`)に入れないための実装上の要請。セルへ直接スロット番号を書く
4. **`OWNED_SPREAD_SCALE`(≈90.5)・`BURST_THRESHOLD`(=20)の値**: 仕様は「正規化する」「固定値」としか言っていないため、契約書がこの値の唯一の定義になる
5. **`robustness`(特徴7)の実データ範囲が狭い**: 現行攻撃3種の値は 0.9970/0.9974/0.9976 とほぼ定数で、実戦ではこの次元の学習信号が弱い。死に次元テストは構成した state で判定するので通るが、実測としての制約は[未決定事項](#v6-で新たに洗い出した未決定事項)に記録する

### v5.2 で新たに洗い出した未決定事項

**(a) ~~カウンター表・護衛表のキラリティ(向き依存)~~ → v5.3 で反証済み。真因は「迎撃の照準窓が狭いこと」**

> ⚠️ **この項目の v5.2 時点の診断は誤りだった。記録として残すが、結論は下記に置き換わっている。**
>
> v5.2 では「`src/search/evaluate-interaction.js` の干渉評価が常に『攻撃=side0 / 妨害=side1』でしか行われないので、
> 生成された表は片方の向きでしか成立しない(キラリティ)」と診断していた。根拠は、防御を使うほど先手が有利になる
> という相関(同一方策どうし600試合・side0 の勝率: `defendBias` 0 → 0.2 → 0.5 → 1.0 で **0.548 → 0.623 → 0.742 → 0.729**)だった。
> 相関自体は実在するが、**帰属した機序が間違っていた。**

**v5.3 の直接検証で反証した。** 各攻撃の最良カウンターを、実試合で両方の向き(攻撃=side0/妨害=side1 と、その鏡像)で走らせた結果:

    両向きで阻止 = 8 / 生成向きのみ阻止 = 0 / 鏡像のみ阻止 = 1 / どちらも突破 = 0  (有効サンプル 9)

カウンター関係は**向きにほぼ依存しない**。唯一の非対称例(A8)はむしろ**鏡像側でだけ**成立しており、キラリティ仮説が予測する向きと逆だった。

**真因は照準窓の狭さ。** 攻撃を antX=0 に固定し、妨害の発射列を全256列に振って「阻止できる列数」を数えると:

| 攻撃 | 妨害 | 記録 deltaX | 阻止できる列数 / 256 |
|---|---|---|---|
| A9 | D5 | 60 | **1** |
| A7 | D7 | 230 | 3 |
| A4 | D8 | 60 | 4 |
| A6 | D3 | 56 | 6 |
| A8 | D2 | 46 | 9 |
| A1 | D7 | 224 | 10 |
| A2 | D2 | 172 | 33 |
| A5 | D2 | 156 | 37 |
| A3 | D2 | 166 | 50 |
| **平均** | | | **17 / 256 = 6.6%** |

つまり「どの列から撃てば当たるか」は **(攻撃, 妨害) のペアごとに固有で、しかも極端に狭い**。`counterTable` の `deltaX` はまさにこの情報を持つために存在していた。

⚠️ **v5.3 では方策の判断で `deltaX` を使わない「完全自由な発射列」を選択した**(設計判断。ユーザー確認済み)。
発射列は「狙う相手の現在列 + 学習した単一オフセット `disruptAimOffsetFrac`」で決まる。オフセットは**全ペア共通の1個の数値**なので、
ペアごとに異なる幅1〜10列の窓を狙い当てることは構造的にできない(無作為に狙ったときの命中率の目安が上記 6.6%)。
**その結果、迎撃は実質的に機能せず、CEM は `defendBias` を 0 に収束させる。** これは既知かつ意図された割り切りであり、
「防御が使われない」ことの現時点の直接原因はキラリティではなく**ここ**である。

防御を機能させたくなったら選択肢は3つ: (1) `deltaX` を照準の基準に戻し学習オフセットを上乗せする、
(2) オフセットを (攻撃, 妨害) ペアごとの表として学習する(方策の次元が一気に増える)、
(3) 照準窓が広くなるように妨害テンプレートの選抜基準を変える(要テンプレート再生成)。

**(b) 護衛が実プレイでほぼ発射されない**

護衛の発射窓とトークン経済が噛み合っていない。攻撃9種のうち、次の判断(670ステップ後)までに間に合う護衛タイミングを持つのは **5種(A1, A3, A5, A6, A8)のみ**で、残り4種(A2, A4, A7, A9)は `fireAtStep` が 0 の候補しか持たない。さらに実際に払えるのは妨害コストが小さい組だけ(D2 = 6、D3/D6 = 5 に対し D1 = 19、D7 = 18、D8 = 17)。

実測: `escortBias = 1` にしても妨害の発射数は **0.00〜0.03 回/試合**(攻撃のみの方策と同じ)。バランス指標「攻撃＋護衛 vs 同じ迎撃の突破率 100%」は `simulate-matches.mjs` の**独立した部分実験**で測っており実プレイの値ではないため、この欠陥は指標に現れない。

⚠️ **`cpu.js` 側の対処は2つ試して、どちらも効かなかった**(同じことを再試行しないこと):
1. **見込み残高での採否判定**(`projectedTokens`)。「発射の瞬間は残高がほぼ0だから候補が全部落ちるのだろう」という仮説。→ 発射数は変わらず。ただしこれ自体は正しい予算計算(予約は未来に発火する)なので**採用したまま残してある**。
2. **失敗した攻撃アリへの再挑戦**(`escortedAtSteps` の打ち切りを外して毎判断リスキャン)。「トークンは時間で増えるのだから後から払えるはず」という仮説。→ 発射数は 0.00 のまま変わらず、スループットだけ約半分(130 → 66 試合/秒)になったので**元に戻した**。A8 の護衛窓は 16,800 ステップ＝判断25回ぶん開いており、「窓が閉じたら打ち切る」方式でも縮まらない。

つまり原因は採否ロジックではなく**テンプレート側のデータ**(護衛の `fireAtStep` の分布と妨害コストの組み合わせ)にある。**対処にはテンプレート再生成が必要。**

⚠️ **その結果 `escortBias` は学習信号を持たない死に次元になっている。** 出荷している `data/policy.json` の `escortBias = 0.655` は**学習された値ではなくランダムウォークの残骸**。実測(出荷方策を基準に `escortBias` だけを 0 / 0.25 / 0.65 / 1.0 に振り、各400試合・共通乱数): 勝率はすべて 0.5 の ±2σ 以内で有意差なし。この値を「CPU は護衛を6割の確率で使う」と読んではいけない。

**(c) 迎撃は現在のコストでは割に合わない**

実測(120試合・相手は攻撃のみの方策): `defendBias = 1` にすると自分の攻撃発射数が **9.97 → 1.92 回/試合**に落ち、妨害が **18.34 回/試合**になる。得点は **3.83 → 1.24**。`tryDefend` が `??` チェーンの先頭にあるため、敵の攻撃が見えるたびに迎撃を優先して攻撃が枯れる。飛行数上限(`MAX_FLYING`)による判断潰れは 0.0 回/試合なので、**枠ではなくトークンと優先順位の問題**。
